# 0.95.22 — the obsidian mine equips its pickaxe instead of "mining" with a water bucket (G108 natural terrain)

Follow-up to 0.95.21. Fixes the deadlock that stalled the natural-terrain portal on the obsidian
MINE: the miner never equipped its pickaxe, so it "mined" exposed obsidian with the flood's water
bucket in hand, forever.

## The deadlock

After flooding a lava lake, the bot mines the obsidian it made. Measured on the `nether-reach`
checkpoint: the bot sat 7+ minutes on "Destroy block at 787,21,817 / Block in range, mining...",
obsidian count stuck at 0, holding a `water_bucket`. Ground truth: the target was real, EXPOSED
obsidian and a diamond pickaxe was in the pack -- but the pickaxe was never equipped, and you cannot
mine obsidian with a bucket.

Root: `DestroyBlockTask.equipBestToolFor` skipped the tool equip whenever
`PathExecutor.isPlacingNow()` was true. That is QUEUE-based (`placeQueue != null && !isEmpty()`,
PathExecutor:332), so it is true whenever a STALE place/bridge segment lingers in the queue -- which
it does after the natural-terrain route to the obsidian -- not only during an active place. So the
guard fired every tick, the pickaxe was never equipped, the bot could not break, and the queue never
drained: a self-sustaining deadlock. The flat bench never hits it (the trivial route queues no place
segment), which is why the build was 6/6 there.

Proven in isolation on the live stall: manually selecting the pickaxe let the bot break the obsidian,
and the auto-equip then worked -- so mining is fine once the tool is in hand; only the equip was
blocked. It is not hunger (food 20/20) and not a main-inventory reach problem (a hotbar pickaxe was
skipped too during the stall).

## The fix

Remove the `isPlacingNow()` guard from `equipBestToolFor`. Every caller is a BREAKING context that
has just claimed the tick (`minerMineUntilMs`/`minerAimUntilMs` set immediately before), so the
executor yields and will not place this tick -- the miner owns the hand and must equip its tool. The
FoodChain-is-eating guard stays.

## Validation (natural terrain, `nether-reach` checkpoint)

| | 0.95.21 | 0.95.22 |
|---|---|---|
| obsidian mined (held a pickaxe) | 0, stuck 7+ min with a water bucket | **0 -> 14** |
| reached the frame build | no | **yes** (placed 10 of the obsidian) |

The bot chained the full natural-terrain path: food buffer -> flint -> flood -> obsidian rung ->
mine 14 obsidian -> "Building nether portal with obsidian" -> place the frame. It did not light the
portal inside the 24-minute window (natural terrain + underground mob combat is slow, and the frame
build then hit a wander at the build site), but the obsidian-mine deadlock is gone.

## Regression

`equipBestToolFor` backs all of DestroyBlockTask's breaking, so the nav suite's mine/pillar/bridge
courses are the guard: `nav_break nav_wall2 nav_bridge nav_flat nav_staircase nav_descend` **6/6
PASS**. Removing the guard only makes the mining tool equip MORE reliable, so nav_break (mine then
continue) stays green.
