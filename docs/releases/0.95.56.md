# Pillar routes keep their planned clearance

Later pillar steps can reuse the interaction obstructions their route already
scheduled for removal. The planner no longer rejects that cleared source as
non-replaceable or charges the same outline removal twice. Placement permission,
world border, protection hooks and recent failed-placement memory still apply.
`pillarUsesBranchClearance` is enabled by default.

**HOW TO TEST:** on the flat bench, run the controlled cave-vine interaction
fixture. It must build all three requested rungs in the requested column, finish
grounded and keep interactive support blocks from opening their interfaces:

```powershell
python deploy/runner/pillar_interaction_test.py --support smoker --cave-vines --navigator --vine-tip-offset 1 --freeze-random-ticks --tag branch-clearance --output-dir deploy/runner/artifacts/branch-clearance
python deploy/runner/run_suite.py nav --only nav_flat,nav_staircase,nav_descend,nav_water,nav_wall2,nav_bridge --repeat 6 --record
```

Seventy-two dry trials used six balanced OFF/ON pairs on rebuilt fixtures. The
single-vine-tip requested-column gate changed from0/6 to6/6; two tips passed6/6
in both arms. Furnace/vine placement and ceiling/protected refusal passed6/6
per arm. Forty-two adjacent navigation/construction cases also passed with both
experimental settings enabled. Every recording was inspected at2s; this is
sampled visual coverage, not every-frame inspection or a speed claim.

The final packaged defaults passed36 valid navigation trials: six repeats each
of flat ground, stairs, descent, water, ledge construction and bridging, with
branch clearance ON and water pillar input OFF. Minimum average FPS was28.5;
sampled health stayed20 and measured logs had no runtime errors. Every film was
inspected at2s. Execution used two phases:25 original passes plus11 continuation
passes. One extra original staircase attempt lost its full verdict to a Windows
output-reader error; its video and error are retained and excluded from the score.
Water pillar input remains experimental and OFF by default. Native food pursuit,
lava collection and the complete playthrough remain open.

# Bench processes and recording ownership

Unattended test wrappers launch Windows console children without desktop console
windows while keeping captured and inherited output, return codes and timeouts.
Deliberately interactive launches and POSIX behavior keep their normal semantics.

**HOW TO TEST:** `python deploy/runner/test_process.py`. Actual Windows13/Linux12
checks passed with platform-specific skips. Session1 Docker probes preserve both
streams and exit7; sampled desktop monitoring observed no new visible console.

An owned gamer recording remains live through the confirmed driver stop before
final diagnostics and checkpoint saving. Finite recordings still expire for
short callers. Actual idle ownership, normal return, catchable exit and raw native
capture-boundary checks passed; forced OS termination remains outside coverage.

**HOW TO TEST:** resume an existing checkpoint with
`python deploy/runner/gamer_smoke.py 5 --from NAME --raw-resume --record`.
`GAMER_WINDOW_END` must report an inactive runner, and the finished recording must
cover the span since `GAMER_CAPTURE_START`. Native progress is judged separately.
