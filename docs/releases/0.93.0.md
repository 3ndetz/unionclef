# 0.93.0 — "distance from start" in the coarse search was not a distance

## The bug

`BlockSpacePathFinder.getDistFromStartSq` computes the Y and Z terms from `start.x`:

```java
double xDiff = start.x - n.getPos().x;
double yDiff = (fix ? start.y : start.x) - n.getPos().y;   // start.X minus node.Y
double zDiff = (fix ? start.z : start.x) - n.getPos().z;   // start.X minus node.Z
```

`fix` is `smartMoves`, which ships off — so this was the live arithmetic. It broke two things at
once, and both had been chased separately for days.

**A gate that is always open.** `bestSoFar` may only hand back a partial path that progressed more
than `MIN_DIST_PATH` (5 blocks in that class), and it tests that against this quantity. With the
bot at x=1792 the term `start.x - n.y` is about 1700; squared, it is millions. The gate passes
whatever the real progress was, so partial paths that go nowhere reach the physics leg, which is
handed a route from a cell to itself and stops.

**A counter that cannot fire.** `salvage()` opens by computing `movedSq` from the same call and
returns early when `movedSq > MIN_DIST_PATH * MIN_DIST_PATH`. Always huge, always early-returned,
so `bsStub++` was unreachable. It read 0 on every run, and a previous pass took that zero to mean
there were no stubs to salvage.

## What it was doing to the run

The physics leg's own halt counter, `gvpTinyGuide`, had been printing this in the verdict line all
along and nobody had read it:

```
before (broken arithmetic, 12 runs):  290 halts, 251 on a route to nowhere  (87%)
after  (fix on by default,  6 runs):  189 halts,   5 on a route to nowhere  ( 3%)
```

That pair is a before/after across builds, not a paired A/B — terrain and time are not held. The
paired figure is the coarse search's own output on shared ground, three runs an arm:

```
fix arm     2, 0, 0     nowhere-guides per run
control    96, 89, 109
```

## Why it ships on correctness, not on a stall number

`coarseDistanceIsADistance` defaults **on**. The case is:

- the arithmetic is simply wrong — `start.x` cannot belong in the Y and Z terms;
- nav, interleaved A/B, three runs an arm: **18/18 with the fix against 16/18 without**, and
  `nav_staircase` — the historical "course A", the one this file warned lives on the garbage
  partials — is 3/3 in BOTH arms. Both failures fell to the control;
- the full nav suite on the shipped default is 26/28, and both stragglers (`nav_ladder`,
  `nav_notch`) are 3/3 in a follow-up A/B, so they are stand flake.

**The playthrough is NOT established**: 8 informative pairs, stall time −29 s per run at t ≈ −0.6.
Rungs cleared the bar in one sweep of three and that number is not quotable here — a stall fix is
scored on stall time (checklist 4a2), and the arm that runs first inherits an unfelled forest
(4a3), which is the fix arm.

`smartMoves` bundles this repair with a different `bestSoFar` branch and stays **off**: measured as
a bundle it lost rungs and shuttled more.

## Also in this release

New diagnostics, all counted in blocks rather than nodes: `guideSrc` (which search built the guide
and whether it went anywhere), `trunc` / `fastNowhere` (routes flattened to a single cell because
the first hop needed mining — 95% of the fast planner's share), `coarseNowhereBy` (the exit each
bad coarse guide left by), `arrivedAtSnap`, and `wallAlreadyAir`.

`wallSkipRefused` was counted **behind the very flag it measures** and so could only ever read 0.
It is now split: `wallAlreadyAir` counts the occurrence unconditionally, `wallSkipRefused` the
refusal. Measured: `wallAlreadyAir=0` over three runs, so the documented "mine nothing, loop"
stall is not occurring and `wallShortcutNeedsAWall` has no material.

## Suite at release

`nav` twice through: **26/28**. `nav_wall2` failed once and then went 6/6 on a re-check, so that
one was flake. `nav_bridge` is genuinely flaky and it is **not this release's doing** -- pinned
off it scores 3/6, pinned on 4/6, so the arithmetic repair is if anything marginally the better
arm and neither reading separates from the other at n=6. It is recorded as an open flaky gate
rather than treated as a blocker, because it fails the same way on the code this release
replaces.

## Known not-fixed

- `arrivalAgreesWithTheSnap` stays **off**: 6 pairs, stall −78 s per run at t −0.53, and the three
  informative pairs disagree in sign. It repairs the last step of a walk that mostly does not
  happen.
- The fast planner is accepted on `fast.path.size() >= 2` — a check in nodes, which cannot tell a
  stub from a string-pulled corridor.

## How to test

```
python3 deploy/runner/run_suite.py nav
python3 deploy/runner/gamer_smoke.py 10 --repeat 6 --pin-alt coarseDistanceIsADistance=true
python3 deploy/runner/paired_ab.py <log> --flag coarseDistanceIsADistance --counter bsStub
```

`bsStub` is the mechanism counter: 0 in the control arm by construction, non-zero with the fix —
which is itself the proof the formula changed.
