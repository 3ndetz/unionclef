## Four capabilities were dead, and every suite was green

This release is the flee/dodge half of the baritone port. Along the way it found four things the
bot was not doing at all — none of which any course could see, because a task that produces an
untranslatable goal fails silently: it returns, the chain ticks, the debug string says something
plausible, and the body never moves.

The test that found all four is the same question asked four times: **what does the DRIVE
receive?** Not what the task looks like it is doing.

| what | why it was dead |
|---|---|
| walking out of **dragon breath** | `GoalRunAway` is not one of the six types `goalToVec` translates, so the drive got `null` every tick |
| **dodging arrows** | `GoalDodgeProjectiles` is a pure predicate with no position at all — nothing to steer at |
| **dragon-fight steering** | both sites called `setGoalAndPath` on the legacy engine, guarded by `Nav.hasGoal()`, which reads that same dead process and is therefore always false |
| **creeper fuse-awareness** | `getCostOfEntity` is only ever read through `heuristic()`, and heuristic is consumed exclusively by shredder's A* |

Standing in dragon breath is one of the two things that kill a bot in the End, and the bot had no
way to leave it.

## The blocker on the flee port was the CALLER, not the goal maths

The note against this work said the risk was live-versus-snapshot entity positions. Re-reading the
sources found something sharper: `CustomBaritoneGoalTask.goal()` caches the goal object for the
life of the task and **never invalidates it**. `AltoGoal.Flee` is a record holding a finished
point, so a cached `Flee` is a *fixed destination* — the bot would run to wherever the mobs stood
when it started and stop there while they followed it.

The live behaviour never came from the cache being refreshed. It came from `goalToVec`
re-interrogating baritone's goal object every tick. So any port that hands over a snapshot changes
behaviour even though the types line up — and that is a property of the caller, not of either goal
type.

`AltoGoal.FleeLive` is therefore a class rather than a record, recomputing `target()` from live
positions at most once per tick — the same guard `NearestSatisfying` already used in that file.

**Direction comes from the centroid, not upstream's average of unit vectors.** Unit vectors cancel:
two mobs on opposite sides sum to nothing, the old method returned null, the drive got no point and
the bot stood still between them. A centroid degrades to "any direction" instead of "no direction",
which is what a cornered bot needs.

## A bench criterion that could never be true

```
yield Criterion("bot survived", ctx.deaths == 0, f"deaths={ctx.deaths}")
```

`ctx.deaths` is a **method**. This compared a bound method object to `0` — always false — and
printed `<bound method Ctx.deaths of ...>` as its detail, which is how it was spotted. The mirror
image of a check that cannot fail, in a suite written the same day the checklist gained a rule
about exactly that. Swept the whole bench for the shape: `self_falls` and `freeze_windows` are
fields and are used correctly everywhere; `deaths` is the only method used bare, and this was its
only bad site. Confirmed fixed in a live run — the detail now reads `deaths=0`.

## Known

- **The dragon-fight steering fix cannot be demonstrated by `end_dragon`,** and this release does
  not claim it. The course still records `200.0 -> 200.0`. The cause is the one written down in
  0.73.0's notes: a dragon summoned into a world with no `EnderDragonFight` never PERCHES, and both
  strategies wait on the perch, so the phase the steering belongs to is never entered. A real
  dragon course needs a genuinely generated End entered through a portal.
- **`allround` is the only gate failure in the bench,** and its single failing criterion is
  `bot deaths <= 0` in a mutual sword duel. It fails on every jar (`deaths` 2, 2, 1). That is the
  honest state of a fight the bot loses, and it sits below the frame rate at which the guard
  considers melee judgeable at all.
- **`DodgeProjectilesTask` searches from a fixed origin.** `NearestSatisfying` takes its origin at
  construction and the task caches its goal, so the dodge always expands from where the bot stood
  when it began. The predicate is live; the origin is not. Tolerable only because that task carries
  a timeout and is recreated — the flee family needed a whole new type for exactly this reason.
