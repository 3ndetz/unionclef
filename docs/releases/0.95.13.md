# 0.95.13 -- a decisive unreachable-verdict keeps a block's normal retry generosity

A follow-up to the Finding B fix in 0.95.12. The decisive give-up verdict (`blackListNow`) excludes
an unreachable target at once, but it was passing an allowed-failures of 1 to the shared
`blackListItem`, which overwrites the block's stored threshold on every call. So after a decisive
verdict a block kept a threshold of 1 (not the ordinary 4) until some other caller happened to
re-blacklist it -- meaning once the cool-off lapsed it could be re-excluded after a single ordinary
failure instead of the usual four. That contradicts the intent ("stays evidence -- the target is
offered again with the same generosity"): a decisive verdict should exclude the target NOW, not make
it permanently stricter to retry.

## The fix

`blackListNow` now passes the ordinary default allowed-failures (4, matching `requestBlockUnreachable`)
and pushes the failure count over that threshold, so the block is excluded immediately AND keeps its
normal retry generosity after the cool-off. Behaviour is otherwise unchanged: still evidence, never a
permanent `deliberate` exclusion; the cluster condemn (`requestAreaUnreachableNow`) and the dig-route
per-block path are unaffected.

## Verified

Canopy wedge bench (`deploy/runner/canopy_log_reach_test.py`) still PASS -- the bot condemns the
unreachable canopy in one verdict and goes exploring. Regression subset (canopy recovery, tree_reach,
self_floor_dig) PASS.

## Known, not fixed

- The nether portal does not yet build reliably end-to-end in cramped mined terrain (G108); a clean
  fix is a dedicated redesign of the obsidian cast/gather (see docs/ai/progress.md).
- Death by cave-mob nest during deep mining still loses the base; combat/survival, not pathfinding.
