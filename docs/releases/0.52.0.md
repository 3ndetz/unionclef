# 0.52.0 — follow actually chases a moving target (LIVE-A fixed)

`@follow <player>` (and any follow / combat approach) now tracks a MOVING target
tightly instead of "forever rebuilding the route and standing still" / lagging
~30 blocks behind. Stand test: average distance to a victim looping at ~3 blocks/s
dropped from **~30 → ~1.4 blocks**.

## What was wrong (three layers, found by instrumenting, not guessing)

1. **Routing**: `@follow` ran on baritone (altoclef `FollowPlayerTask` →
   `GetToEntityTask`, `TungstenHelper.primary` defaults false), whose moving-target
   failure mode is exactly "re-plan forever, stand still". Now it drives the tungsten
   follow engine.
2. **Stale target**: the tungsten walker's DIRECT sprint aimed at a ~2s-old snapshot
   of the target set once at `start()`. Now `steerLive()` re-aims the drift-immune
   sprint at the target's LIVE position every tick, so the bot cuts across and closes
   instead of tracing the target's past path.
3. **The real killer** (found via the walker's per-tick DEBUG log): DIRECT bailed
   "danger → BFS" on nearly every tick, so the drift-prone physics executor did all the
   moving (slow, drifty, never closed). The danger check scanned `hasHolesOnPath` over
   the ENTIRE straight line to the 20-block-away target — any hole anywhere on that line
   killed the sprint. Far hole/void avoidance is the BFS/physics job; the DIRECT sprint
   only needs the IMMEDIATE ground safe. Now it checks the next ~4 blocks (a rolling
   lookahead that still bails before a real void as the bot advances).

Also: a bail cooldown so a genuinely-blocked steer yields to BFS+physics to route
around; bot-displacement stall detection (a moving target makes distance-shrink the
wrong "stuck" signal); and a floor added to the follow stand arenas (a wandering bot
could fall into natural-terrain holes).

## Scope / safety

DIRECT / `tickDirect` is used ONLY by the follow engine (follow + PunkPlayer APPROACH);
terrain nav (`@goto`/`@get`) uses `startBFS`/`tickBFS`, untouched. Combat COMBAT-mode
stops the follow engine, so no conflict with `combatMove`.

## How to test

`deploy/runner/follow_altoclef_test.py` (@follow) and `follow_test.py` (`;followPlayer`):
victim tp'd around a loop at ~3 blocks/s; follower must keep avg dist < 10, keep moving,
≤ 3 freeze windows. `follow_diag.py` dumps the walker's per-tick decisions
(move-gate %, speed, LOS, bail reason) for future follow-nav work.
