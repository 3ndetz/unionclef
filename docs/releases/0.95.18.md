# 0.95.18 — a structure pillar stays in its target column (G108 misdirection backstop)

Follow-up to 0.95.17. Closes the misdirection half of the full-flood churn; the high-cell placement
stall is documented as the remaining ceiling.

## The misdirection: the build pillar cast obsidian into the bot's drifted column

Frame cells with no reachable SIDE stand (column tops, top row without the scaffold) fell through the
build queue's PILLAR branch, which sends the body to stand IN the target cell — a 1-wide obsidian
wall over the open portal interior — from which the body slides to an adjacent column. `PillarTask`
then cast the named structure block into whatever column the body was in, verifying only against the
body's own cell, not the frame target. So obsidian landed at x-1/x+1/interior, the frame re-read
incomplete, and the re-gather mined the misplaced block back — churning until the finite lava lake
drained ("Searching for a lava lake … Wander for Infinity"). Root-caused by a sub-agent trace: the
off-plane landing on BOTH sides is the pillar-drift signature, not a face-selection bug.

- **`PillarTask` + `BlockPlaceHelper`:** a structure-block pillar is now pinned to its target column
  (`startTo(ty, block, tx, tz)`); the place gate refuses any cell whose x/z is not the target, so a
  drifted body can never cast the structure block off the target column. A nav climb (no target
  column) is unaffected. This is the correct backstop — the structure block can only land where it
  belongs.

## What was tried and reverted

Extending the front scaffold to the column tops (raise trigger `y>=origin+2` instead of `==origin+3`)
was measured a NET REGRESSION on the full flood (0/2 vs 0.95.17's 3/4): it adds the scaffold's own
high edge cells (dy=2), which have the SAME high-over-open-space stall as the frame cells they were
meant to help. Reverted.

## Known issue (the remaining ceiling) — stall DETECTION works, stall RECOVERY does not

The full flood still intermittently stalls (~1 in 4) on a cell placed over open/narrow build terrain
— the top-row middle (2358,-53,358), a left-column cell reached from a 1-block step at the frame's
west edge, or a scaffold top edge. This session made stall DETECTION comprehensive (the shimmy grace,
and a per-cell parked-aim timer that fires reliably — verified in the logs). The blocker is stall
RECOVERY: the escape wander (`TimeoutWanderTask`, tungsten nav) cannot relocate a body trapped at the
build — measured, the bot bobbed in place ~180 s at a 1-block step west of the frame, "Wander for 4.0
blocks / Exploring", never covering an inch, because tungsten nav cannot path off that spot (a likely
factor: the spiral wander sometimes targets a point ACROSS the frame, and nav jams against the
obsidian wall). The per-cell escape timer (a working detector) was reverted because its recovery
wander froze the same way — detection with no working recovery only trades a place-freeze for a
wander-freeze. The real fix is a recovery that reliably relocates a build-trapped body (a DIRECTED
step to a known-clear approach cell away from the frame, or a sturdier/wider stand so the bot never
gets trapped), tracked as the next pass. This is the deep nav+build seam NAVIGATION.md flags as
known-hard.
