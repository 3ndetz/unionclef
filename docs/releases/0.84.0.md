## The knockback predictor never hit the ground, so the retreat stage was on for the whole fight

`SafetySystem.simulateKnockback` integrated fifteen ticks of gravity with **no collision**, so the
simulated body fell through the floor. Replaying the loop exactly:

```
vy starts 0.4      peak of the arc   +1.153 blocks
15 ticks later     final offset      -2.331 blocks
```

The caller then measures `VoidDetector.fallHeight` **from that sunken point**, and `DANGER_BATTLE`
engages at `fallHeight >= 4`.

On ordinary terrain the sunken point sits inside solid blocks, `fallHeight` reads 0, and nothing is
visible — which is why this survived a long time in a comment as the estimate being merely
"inflated on flat ground". On a **thin platform it is total**: the mob arena floor is a slab at
y=-61, `floor(-60 - 2.331) = -63` is *under* it, and below that is void, so `fallHeight` returns
`MAX_SCAN_DEPTH` and the stage engages every tick wherever the bot stands.

That is not cosmetic. `DANGER_BATTLE` sets `repositioning = true` and steers along
`pathfinder.getRetreatPath()` — so the bot spent its fights walking **away** from the target,
driven by a simulation artefact rather than by anything in the world.

**Measured on `mob_skeleton`, same course and same arena in both arms:**

| | before | after |
|---|---|---|
| `danger` | 69 / 144 / 170 / 222 / 244 / 1984 | **0 / 0 / 0 / 0 / 0 / 0** |
| `reposition` | 39–92 | **0** |
| `enemy` (aim owner) | 0–9 | **55 / 63 / 55 / 76 / 69 / 58** |
| score | 1/6 | 1/6 |

The aim belongs to the **enemy** now instead of to a retreat path, in every run. **The score did
not move**, and both halves of that are the result: a real defect is gone, and it was not what was
keeping this course red.

The caution itself is **not** removed — removing it was measured harmful twice (deaths 16 → 23 and
15 → 19) and that result stands. Knocked over a real ledge, the simulated body still ends in open
air with nothing beneath it and the stage still fires there. What stops is it firing on solid
ground.

## The course was scoring its best result when the fight did not happen

Three defects in `mob_skeleton`, all found by making one dead instrument work.

The skeleton-position sampler hung off `drive_tick` behind `int(elapsed) % 2`, and these runs
early-stop the moment the target dies — so it collected **nothing**. Every run has printed
`closest_gap=None` for as long as the line has existed, which was read for several sessions as
"the bot never gets close" when it actually meant "never measured".

With it sampling from `early_stop` instead, the pass condition turned out to be met by the target
**leaving**:

```
FAIL min_hp=13   3 swings landed        FAIL min_hp=12   3 landed
PASS min_hp=20   2 landed               FAIL min_hp=20   1 landed, never observed alive
```

A skeleton has 20 HP and does not die to one swing. "The skeleton is dead" and `early_stop` both
ask a single question — has the entity stopped existing — and vanilla offers two ways to do that
without losing a fight:

1. **The void.** The arena is a floating island and this course spawned the skeleton at x=12.5 with
   the rim at 14. Its last known position was x=13.7 in *every* run where it was seen at all: a bow
   mob backs away from an approaching enemy, and here "away" ran out. A skeleton in freefall does
   not shoot, so `min_hp` read 20 and the course went green on a fight that never happened.
2. **Despawning**, which widening the arena made *more* likely by giving it room to keep retreating
   — last seen at x=20.5, against vanilla's 32-block despawn range. `PersistenceRequired:1b`
   removes that path, so a skeleton that is gone was killed.

The course now has its own field at `half=30` (approach, kit, spawn and gates untouched), and the
void check demands **positive evidence** — "seen alive on the arena" — because the obvious
`not fell` spelling passed four runs out of four on `last_seen=None`.

⛔ **Rule 4j applies:** every number recorded on `mob_skeleton` before this — including the 17% pass
rate and the 53-run ruler — was measured on a different course and must not be compared with runs
after it. The honest baseline on the repaired course is **1/6**.

And one consequence that cuts against the score, recorded rather than buried: with the arena
widened the skeleton retreats to x=29.7 instead of being pinned at 13.7, so the chase and the time
under fire are **longer** than on the old course. It is now honest and harder at once.

## Two filed defects that turned out to be defects only in the reading

Both were on a list produced by re-reading shipped code, and both were checked rather than assumed.
The reasoning now lives at each site so a later pass does not "fix" them.

- **"The shooter guard scans to 12.0 while `mob_skeleton` spawns at 12.5."** `isInDanger`'s own
  hostile scan uses `reach = (health <= 10 && !witchNearby) ? 12.0 : 8.0` — 12.0 in exactly the
  state where the flee branch bids. The guard is never narrower than the test it guards, and beyond
  12.0 there is no flee bid to decline.
- **"Register `ProjectileDodge` in the `tungsten$driving` predicate."** That predicate has one
  consumer — the leaked-input release — and it touches only sneak/attack/use. `ProjectileDodge`
  presses only WASD and sprint, so registering it would not affect a single key it owns. Its own
  release already exists, which is the stronger arrangement anyway.

## Also in this build, switched off

`combatHoldContactOnShooter` (default **false**, inert). Against a `RangedAttackMob` it drops
sprint at the swing rather than at `TriggerBot.REACH`. The reason it exists: sprint is cut inside
3.0 so the blow lands unsprinted, but a skeleton retreats at about a walking bot's speed, so the
tick the bot crosses 3.0 and slows to a walk it falls back into the 3–6 band — which is exactly
where the arrows land (`gapMean` 3.79–5.03, `gapMax` 6.30, past what any dodge can beat).

It is **unmeasured** and ships off deliberately, to be judged as a pinned same-session pair
(`run_suite.py --pin combatHoldContactOnShooter=true`) on arrows landed rather than on pass count.
Zombies and players take the byte-identical old path, so nothing else in the suites can move.

## Checklist rule added

**4n — a gate that tests for an absence can be satisfied by things that are not success.** Enumerate
every way the observable can occur without the behaviour under test; prefer removing the
alternative to detecting it; pair the absence with a positive counter that must agree; and make the
criterion fail on missing data.
