# 0.95.16 — a build shimmy is a stall (G108 portal reliability)

Follow-up to 0.95.15. The remaining intermittent post-iron portal stall is fixed at the core, and
the bench that measured it is corrected.

## The stall was a shimmy, not a freeze

When a placement could not reach its stand, the build drain did not FREEZE — it SHIMMIED, oscillating
the body ~0.4 blocks a tick against the cell. Measured on the portal front scaffold: the body sat at
(2359.5,-56,359.5)±0.4 for 75+ seconds under "Placing cobblestone at 2359,-57,360", the frame never
completing. The stall detector missed it twice over:

- **`MovementProgressChecker`**: `resetIfPathingWithGrace` used a FOLLOWING anchor with a 0.02-block
  per-tick bar, so a shimmy cleared the bar every tick, `ticksSinceMoved` never grew, and the grace
  reset the detector for ever. Now it uses a FIXED anchor and a 1-block NET-distance bar: a shimmy
  stays inside the radius and accumulates the grace; a real walk or pillar leaves it and re-anchors.
  Exposed as `stalledInPlace()`.
- **`PlaceBlockTask`**: wanders on `stalledInPlace()` too, so an in-place shimmy is escaped like a
  freeze. The escape wander MOVES via tungsten, and so does the build drain, which kept re-issuing
  `FastNavigator.startExact` every tick — two owners of one nav singleton froze the body for 50 s
  under "Wander … Exploring". The wander trigger now releases the drain first (`clearQueue` +
  `FastNavigator.stop()`), leaving the wander sole owner; the cell is re-submitted once it ends.

The change is general to all block placement and on the real @gamer path (`EnterNetherPortalTask` →
`ConstructNetherPortalObsidianTask` → `PlaceBlockTask`).

## The bench: a teleport is not a failure

The bench scanned for a `NETHER_PORTAL` block within radius 10 of the BOT, client-side — which only
sees chunks loaded around the body. A freshly lit portal teleports the body that lit it: the bot
walks into its own portal, is sent to the nether, the overworld build chunk unloads on the client,
and the near-bot scan then finds nothing. Every such run was reported FAIL though the portal had
built AND lit AND worked. The bench now reads the bot's dimension server-side each poll; entering the
nether is a definitive PASS (on the wiped flat stand the only portal is the one just built). Setup
forces the overworld dimension first so a prior run cannot taint the latch.

## How to test

```
OBS=1 GIVE_OBS=1 python3 deploy/runner/nether_portal_test.py   # build + light, isolated
OBS=1 python3 deploy/runner/nether_portal_test.py              # full flood -> gather -> build -> light
```

PASS = a real `minecraft:nether_portal` at the build, or the bot teleporting to the nether.

## Test results

- **GIVE_OBS build bench: 8/8 PASS.** Two of the eight hit a shimmy and BOTH recovered in one wander
  (body relocated, resumed placing, "done constructing"). Six were clean at ~63-70 s, wanderHits=0.
- **`mob_melee` combat regression: PASS** (30 fps, zombie killed, no premature wander) — the
  shared-utility change does not regress the combat path.
- **Full flood (real path): builds end to end** (measured 275 s: flood → gather → build → scaffold
  removal → light → portal).

## Known issue (the remaining ceiling)

The full flood still has a rarer, distinct failure: a top-row frame cell can be lost during the
scaffold-removal phase, after which it is re-gathered and the re-placement can stall (the bot ends up
behind the scaffold, out of reach). This is separate from the shimmy fixed here and is the next
target.
