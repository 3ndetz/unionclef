# 0.63.0 — parkour moves: gaps and a steep climb, and the bot breaks through walls

Obstacle course (`deploy/runner/run_suite.py nav`): **3/10 → 5/10**.
**2/3/4-block gaps over the void** and a **steep climb** pass for the first time. Both
courses had never passed before.

| course | before | after |
|---|---|---|
| `nav_gaps` | never passed | **PASS**, 7.8-9.6 s, 0 self-falls |
| `nav_steep` | never passed | **PASS**, 8.5-8.7 s, stable 5/5 |
| `nav_flat`, `nav_staircase`, `nav_descend` | PASS | PASS (no regression) |

## Parkour: five dead spots in a row, in one chain

Each one proven by the log, not by reasoning.

1. **The handoff of a jump to physics did not exist.** `FastNavigator` cut the segment at
   the jump and set a "physics takes it from here" flag — a flag that was **never read,
   not once**. The bot reached the edge of the gap, and nobody executed the jump.
2. **A trap zone between two thresholds.** The path waited for the walker only if its
   start was farther than 2.0, while execution bailed out at a 0.8 discrepancy. Anything
   landing in between started up and died on the very first tick: `drift 1.723 blocks at
   tick 1`.
3. **A partial plan was discarded.** The hint for physics was taken only if the route was
   complete — but on a jump handoff it is incomplete precisely because the jump is
   delegated to physics. The request went into the old search and got `Ran out of
   nodes`.
4. **The walker trampled the jump.** Right after the handoff a new walking segment
   started, and keys were pressed during the jump — two owners at the most sensitive
   moment.
5. **`MAX_JUMP_GAP = 3`** made every 4-block gap unplannable (vanilla clears 4 with a
   sprint jump). Plus the "dead end" branch **printed** "physics owns this" and called
   `stop()`, zeroing the goal — physics was never called. Plus `setPath()` wiped out the
   `;goto` retry callback. Plus an unconditional `sleep(500)` on every request turned a
   58 ms search into "558 ms".

Also: `find()` was `void` and **silently dropped** a request when the search was busy,
and `thread` was not `volatile` and was cleared after `active` — a window in which a
valid request would vanish. That was the source of the ~30% flake rate.

## Breaking through: from "not a single mention in the code" to a punched-out passage

`FastPlanner` — the planner that actually drives the bot — **did not know the word
"break"** (grep for `allowBreak`/`BreakRules`/`toBreak` gave zero). A wall across the
corridor was, to it, an unreachable goal. The receiving side, meanwhile, existed in
full.

A break move was added, priced by real mining ticks, with a check against the rules and
against support. Three root causes along the way:

- the "is this cell occupied" check was called with a function that takes an **absolute
  world height**, with the argument `0.1` — i.e. it asked "does the body fit in open
  sky". Every wall block was considered already open, and the move could never fire;
- the planner preferred **climbing over** a 2-block wall (≈30) instead of **breaking
  through** (≈34.6) — but above jump height you can only get up via a pillar, which it
  does not have. A fantasy move: cheaper, shorter and infeasible. Such moves are no
  longer emitted;
- on a "stop" flag the executor **silently wiped the mining queue**, even though when
  digging the path is empty and there is nothing to replay.

Result in the log: `Mining done — passage open` — the passage through the wall is
actually punched out.

## Cleanup

- **Removed settings that did nothing**: `combatExecutorEnabled` and
  `airStrafeMultiplier` — zero reads. They could be toggled with zero effect.
- `AttackTiming.isCritState` (zero calls — which is why there are no timing-based crits
  in combat), `WeaponSelector.reset` (zero calls).
- **`tungsten.json` no longer shadows new defaults forever.** `load()` unconditionally
  re-saved the whole object, so after the first run the file contained every key, and a
  key from the file always beats a new default. The bench had been running for months
  with old combat tuning and visualization turned off, while the source said the
  opposite. Added `configVersion`; the file is not created until a setting is actually
  changed.

## Known issues

- **Red courses: `nav_break`, `nav_wall2`, `nav_ladder`, `nav_water`, `nav_slime`.**
  The passage is punched through by the break, but the route does not resume after
  mining: physics is handed an unreachable goal behind the wall, and the search burns
  ~20 s per attempt.
- `dig up` / `dig down` still don't exist — breaking only goes sideways, one cell.
- Block placement in `FastPlanner` is absent.
- Aim and the combat stage machine tick per frame with no frame-time correction, i.e.
  the tuning depends on FPS.
- A single key owner has been introduced only in COMBAT; navigation still has several
  writers.
