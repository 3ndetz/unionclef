## You cannot outrun an arrow, and the defence chain had been trying to for as long as the course existed

`isInDanger` returns true on `health <= 10` plus any angry hostile in range. The flee branch then
bids **70**, which out-bids the fight branch's **65**. So against a skeleton: an arrow lands, health
drops under the threshold, and the bot runs *instead of closing*. Running changes nothing — the
arrow follows — and it hands the attacker the one thing it wants, which is range. The bot stays
under the threshold and flees again.

The six-run series that showed it, flee ticks against damage taken:

| `mdRet3` (flee ticks) | 10 | 21 | 111 | 332 | 356 | 356 |
|---|---|---|---|---|---|---|
| `dmgTaken` | 8 | **4** | 16 | **36** | 16 | 25 |

The two runs that barely fled took the least damage in the series.

Fleeing is a defence against **melee**: break contact and the damage stops. Vanilla's own
`RangedAttackMob` marks "attacks from a distance", so the fix asks a *property* rather than naming a
mob. When everything endangering us shoots, the flee is declined and the branches below decide —
the fight branch takes it at 65 if it judges the mob beatable, and its own retreat at 80 still fires
if it does not. One melee attacker anywhere in the danger radius settles it the old way, so a crowd
still flees. The case switched off is the pure shooting gallery.

**Measured on `mob_skeleton`, damage taken:**

```
before   4 16 36 16 8 25                        n=6    mean 17.5
after    8 8 3 20 3 7 13 18 5 8 11 4 17         n=13   mean 9.62   (sd 5.78)
```

`mdRet3` reads **0 in all thirteen** — the branch is gone, not merely quieter. Four independent
earlier series put the before-arm at 17.25 / 19.0 / 17.2 / 17.5, so the halved level is well
established rather than one noisy sample.

### The course is still red, and this says exactly why

`mob_skeleton` has three gated criteria. **Two now pass in every run** — the skeleton dies, and
tungsten takes the legs (`mdTung` 38–75). The only one left is `min_hp >= 19.0`.

A correction worth recording, because it nearly became a claim: the skeleton was **already** dying
in the before-arm, and `mdTung` already read 57–115 there. The `mdTung=0` / `kaTung=0` readings this
bug was chased with came from *older builds*, before the airborne fix below and the strike band in
0.82.0. Both arms kill it and both reach striking distance; the only thing this release moves on
that course is damage taken.

## A hop is not a fall, and the interact gate vetoed every jump

`Nav.isSafeToCancel()` refused for **any** airborne tick while tungsten drove. The bot jumps for
crits, jumps to rush a mob and sprint-jumps to dodge arrows — airborne is its normal state in a
fight — and this predicate gates `AbstractDoToEntityTask`'s interact.

```
dte=682/92/0/0/0/213
```

The gate was evaluated 682 times, the bot was **in range on 92** of them, hungry/falling/mlg all
read zero, and the interact never fired once. The bot stood beside a skeleton it was never allowed
to hit. What the guard is actually for is cancelling a path mid-*fall*; ground within three blocks
means mid-hop, so the protection stays where it matters.

```
dteUnsafe    213  ->  0     (both confirmation runs, deterministic)
mob suite    4/8  ->  5/8   (both runs, mob_trio passing again)
```

## The dodge steered by a near-zero vector — fixed, and it measured neutral

Stated plainly because it did not move the number. The comment said "perpendicular to arrow
trajectory"; the arithmetic said `+180`, which is *directly away from the predicted impact point*. A
skeleton aims at us, so that point sits on top of the player, and the yaw of a near-zero vector is
unstable — the dodge direction was noise. It now steers off the arrow's velocity, which is
well-conditioned at any range, with a bias toward the shooter so evading also closes.

```
dodge fix only   4 16 36 16 8 25   n=6   mean 17.5   against a 17.25 baseline
```

Unchanged, and the counters say why: `mdRet2` runs **79 ticks out of 1323**, so that path cannot
decide this course whatever it does. Kept because it fixes a real instability, and it was in the
build for *both* arms above, so the flee measurement is clean with respect to it.

`pvp` was the real risk: the repo records that dropping this flee clause outright took the duels
from 9/12 to 1/12. It is untouched **by construction** — a duel opponent is a player and never
appears in `getHostiles()` — and `melee_basic`, `edge_duel` and `narrow_bridge_duel` all passed, so
that is measured rather than argued. `mob_trio` is inert for the same kind of reason: a zombie is
not a `RangedAttackMob`, so the loop returns false on the first melee attacker and the flee path is
byte-identical.

## A gate that contradicts its own label, recorded rather than relaxed

`Criterion("at most one arrow landed", low >= 19.0)` permits **one point** of damage, and a skeleton
arrow does 2–5 — so the arithmetic demands "no arrow ever landed" while the label says "at most
one". `dw.rangedHits` already counts exactly what the label describes.

The obvious move was to gate on `rangedHits <= 1`. The numbers said don't:

```
rangedHits   1 3 0 4 0 1 1 2 1 0 2 2 4
min_hp      12 8 17 4 17 13 7 2 15 12 5 12 4
```

That passes **7 of 13** — it turns a red gate into a coin. Relaxing a gate to a coin in the same
pass that is trying to move that gate is indistinguishable from tuning to pass, so the threshold is
untouched and the reasoning lives at the site for a pass that is not holding the result.
