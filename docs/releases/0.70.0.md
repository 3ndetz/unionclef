## Five baritone goal classes removed

The dependency on baritone was never an algorithm. It was a **type**, and most of these classes turn
out to be a comparison and a bounds check wearing an interface:

| removed | what it actually was | gated on |
|---|---|---|
| `GoalChunk` | head for the centre, accept any column in the 16×16 | craft |
| `GoalDirectionXZ` | `isInGoal` returning literally `return false` | craft |
| `GoalFollowEntity` | a fallback into an engine that does not drive | **mob** |
| `GoalBlockSide` + the interact goal path | a goal built only to reach `setGoalAndPath` | craft |
| `GoalRunAway` (movement user) | the first that needed a real design | **nav** |

Six files now hold no baritone reference at all.

**Each was gated on the suite that covers its own path**, not the convenient one. Entity following
lives in the mob suite, so a green craft ladder would have proved nothing about it; it got a
before/after there instead (`PASS mdTung 51` → `PASS mdTung 40`, same health floor).

The flee goal was the only one needing a decision rather than a rename. Fleeing is a *direction*,
which is exactly the case `AltoGoal.target()` documents as legitimately having no point: upstream
expressed it as a heuristic that grows with distance, which a **search** can consume but a **drive**
cannot, because a drive steers at something. So the caller computes "away" and the goal stays a pure
record — reading the client inside the type would make its answer depend on when you ask.
