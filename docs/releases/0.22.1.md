# unionclef 0.22.1 — "Alive": @wander (idle-life) + @mirror

Two in-game commands so the agent acts like a live player instead of standing frozen in a lobby.

## @wander — idle-life (input-driven, works in lobbies) ✅ verified live
`@wander [sec]` (default ~10s) makes the bot fidget like a real idle player: look around, glance at
nearby players, do tiny in-place shuffles, and the occasional jump — then it ends on its own. It runs
in the BACKGROUND while the agent keeps chatting/listening. Stop early with `@idle` / `@stop`.

Backed by `AliveTask`, which is **purely input-driven** (look + hold MOVE_* briefly + tryPress JUMP) —
**no pathfinding**. That's deliberate: baritone (`@goto`/`@follow`) can't move in a protected lobby
(it can't break the glass floor and would just pound a block), which is exactly where agents were
standing frozen. Every horizontal shuffle is paired with an equal step back, so the bot stays on its
spot and won't walk off a platform edge.

Verified live on mc.vanilla-game.ru (a glass hub platform): the camera pans across the scene, the bot
glances at a nearby player, and Y stayed constant (no fall) — i.e. it's visibly alive where the old
baritone-based wander stood motionless.

> History: 0.22.0 shipped `@wander` on top of baritone's `TimeoutWanderTask`. Live testing showed it
> does nothing in a protected lobby (the one scenario that matters), so 0.22.1 reimplements it as the
> input-driven `AliveTask`.

## @mirror — record + replay a player's movement (shipped; full live validation pending)
`@mirror <player> [rec|<sec>]` records a target player's trajectory (their position over time,
inferring a jump from upward Y motion) and replays it: the bot reproduces the path + jumps from where
it stands (e.g. copy someone's parkour run). `@mirror play` replays the last recording. `@stop` cancels.

Honest limitations:
- A client only ever observes other players' **positions**, never their raw key inputs. So this is a
  position-faithful, jump-inferred mirror — the bot really walks/jumps the path, it is not a teleport
  and not a frame-perfect input capture.
- The record/replay state machine compiles and is wired correctly, but a clean live validation needs a
  **co-located, clean-named, moving target**. In testing, the two bots landed on different lobby shards
  (couldn't see each other) and nearby random players carry formatting-code names that don't round-trip
  to `getPlayerEntity`. Full parkour-replay validation is deferred to a co-located 2-bot session on an
  open/survival world.

## Notes
Both are TOOLS the agent invokes by its own judgment (no auto-daemon, per the project philosophy:
everything reactive goes through the agent's reasoning). Existing commands
(@gesture/@shift/@get/@give/@follow/@goto/@pursue/@scan/@place/@build/@sign…) are unchanged and are now
documented for agents in mineswarm `agent/shared/game_actions.md`.

Game-pipeline latency measured ~0.9s command round-trip (send → in-game effect), fast enough to play
and converse at the same time.
