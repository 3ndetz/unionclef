## A retry limit of three was being exceeded by a factor of fourteen hundred

`PickupDroppedItemTask` gives an unreachable drop three attempts and then abandons it. The counter
had been printing the contradiction for a long time and it reads as a log line rather than a bug:

```
Blacklist: class_1542['Diamond'/3980, ...]: Try 1920 / 3
```

**1920 failures against a limit of 3, on one entity.** A limit a single target can exceed six hundred
times over is not a limit.

The selector honours the blacklist perfectly well (`EntityTracker:139` skips anything
`unreachable()`); it simply was never consulted a second time. The task blacklists the drop, wanders,
and comes back — but never let go of `_currentDrop`, so the next failure blacklisted the **same**
entity again instead of asking the tracker for another.

### And a second one underneath it: a discarded entity keeps its stack

The same failure path asks "is there a drop, and does it still hold something". Removal does not
touch `getStack()`, so a `removed=DISCARDED` entity answers yes to both **forever** — the task fails
against a ghost. The tracker's own filter has always had this right (`obj.isAlive() && !blacklisted`);
only this branch, which runs off the cached `_currentDrop`, never asked.

Both were found on `mine_diamond`, and the effect is the same shape on the stand:

| | before | after ghost fix | after both |
|---|---|---|---|
| highest `Try N / 3` | **4144** | 1920 | **4** |
| `unreachable` log lines | 4144 | 10 | **3** |
| distinct bot positions in the run | **1 of 75** | 13 of 76 | — |

The first row is the honest summary of the defect: a bot standing at *exactly*
`(-10.7, -60.0, -7.479)` from t=28 s to t=284 s of a 300 s course, at full health, holding its
pickaxe, retrying an item that in one case no longer existed and in the other it simply could not
reach. Three strikes and it moves on now, which is what the 3 was for.

**Tested:** craft suite, **11/12** — every course green except `mine_diamond` itself, which is
the open red described below and was red before these fixes too.

### mine_diamond is still red, and that is not what these fix

The course still returns `diamonds=0` over three runs at 29.5 fps. The retry loop is no longer what
holds it — the counters above say so — but the bot still covers only a handful of distinct positions,
and `y` never leaves −60.0 in any sample, on a course whose whole point is reaching diamond level.
That is a separate thread and it is tracked.

Worth recording how it stayed invisible: this course is the longest in the suite and runs last, so it
collected the stand's wear, and its three readings before today's frame-rate work were INVALID at
13.2 fps, INVALID at 13.0 and FAIL at 16.8 — none of which said anything about the bot. It also fails
identically on the pre-change build, so nothing shipped today caused it. It is a red that starvation
had been hiding, and the frame-rate column added in 0.77.0 is what made it readable.
