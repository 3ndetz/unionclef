# 0.95.15 — nether portal frame build: no more cobble-in-frame churn (G108)

Follow-up to 0.95.14. The frame build intermittently churned (~1 in 4 builds): a frame cell that fell
to the build-queue PILLAR branch was towered with cobblestone (the cheapest scaffold, right for a nav
climb but wrong for a target cell), so the frame-builder found cobble where obsidian belonged,
destroyed it, re-placed, and looped — sometimes recovering slowly, sometimes hard-stalling.

- **tungsten**: a build-queue pillar placing a TARGET cell now towers with the STRUCTURE block
  (`PillarTask.startTo(ty, blockName)` + `equipNamedBlock`), so the frame cell is obsidian. Nav-climb
  pillars are unchanged (still the cheapest throwaway), so navigation is unaffected.
- **altoclef `EnterNetherPortalTask`**: when it must construct a portal it used the fragile bucket
  cast in the overworld, and the caller-supplied obsidian task was unreachable dead code. It now
  prefers the caller's task, else the obsidian method — never the bucket cast.

## How to test

```
OBS=1 python3 deploy/runner/nether_portal_test.py        # full flood -> gather -> build -> light
```

PASS = a real `minecraft:nether_portal` block at the build site (by block id). Frame build should
show zero place/destroy churn on frame cells.

## Known issue (the remaining ceiling)

A deeper, intermittent placement/nav stall remains (~1 in 4-5 builds): the bot sometimes places a
throwaway block at the very cell it needs to STAND IN to place a target (placementStand's side stand
gets occupied, or FastNavigator mis-places while approaching), then gets stuck on top of it. It hits
frame cells and front-scaffold cells alike, independent of this fix. Ground truth from a stall: bot
on cobblestone at (2360,-57,358) — its own side-stand for the scaffold cell (2359,-57,358) — unable
to place. This is a tungsten placementStand/FastNavigator reliability issue and is the next target.
