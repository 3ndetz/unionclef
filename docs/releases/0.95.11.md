# 0.95.11 -- the planner's physics reads are null-safe off-thread too (G107b)

G107 (0.95.10) stopped the block-space search crashing when a background-thread `getBlockState`
returned `null` mid chunk-swap -- but only for the `isIn` predicates it touched. A second-pass
review found the physics simulation (`Agent`) still dereferenced the SAME unguarded off-thread
read in four more places, any of which could NPE the plan the same way (the original G107 crash
was a real mid-flee death).

## The fix (G107b)

`Agent.stateOrAir(world, pos)` returns `Blocks.AIR.getDefaultState()` when an off-thread read is
`null` -- exactly what vanilla's `EmptyChunk` returns anyway, so an unloaded/racing cell behaves
like air for physics (default slipperiness 0.6, velocity multiplier 1.0, `isOf(...)` false). It is
purely additive: nothing changes when the read is non-null. All five racy reads now route through
it: `isClimbing` (from G107), `getVelocityMultiplier` (both reads), the fall landing state, the
slipperiness read and the sneak-check state read.

Verified in the built jar (javap on `Agent` inside the nested tungsten jar shows `stateOrAir` and
the guarded call sites). The race is intermittent and does not reproduce on demand; a normal run
should simply show no `FastNavigator plan failed` NPE and no pathfinding regression.
