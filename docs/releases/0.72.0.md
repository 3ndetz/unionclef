## The bot stood twenty-eight blocks from a crafting table and announced it was on its way

`craft_at_distant_table` has been failing for days. Three separate explanations were offered for it
this week, each measured, each wrong. The fourth was a counter on the decision itself, and it settled
the question in one run:

```
DSIC near=true walk=129.3 makeNew=INF forceEl=true justPlacedEl=true dist=28.0
   ... 224 identical ticks ...
DSIC near=true walk=134.2 makeNew=INF forceEl=true justPlacedEl=true dist=28.2
```

The container task was **correct on every tick** — it found the table, priced building a new one at
infinity, and handed control to the task that walks there. And the distance never changed. The bot
never took a step.

`InteractWithBlockTask`'s out-of-reach branch had become this:

```java
case CANT_REACH -> {
    setDebugState("Getting to our goal");
    clickTimer.reset();
}
```

A debug string and a timer. No goal, no movement.

**This is a regression from this project's own baritone removal.** That pass deleted the goal fed to
`getCustomGoalProcess` on two premises: that the legacy engine no longer drives the body — true, and
still true — and that "something else does the walking" — false. Nothing else does. The measurement
that licensed the deletion (`dxToTable 0.5-0.7`) was taken in a state where something else still
moved it, which is exactly the trap this course exists to catch. It caught it late.

Movement is restored through the **live** path — `AltoGoal.near` via `GetWithinRangeOfBlockTask`, the
same drive the water and lava escapes use — not through the legacy process, which stays removed. The
task is cached in a field; building it per tick would restart the walk every tick.

```
craft_at_distant_table   FAIL -> PASS   6/6
                         pickaxe=True  planks=0 sticks=0  dxToTable=0.4
```

Blast radius is every interaction with a block, so this shipped behind full craft and nav regressions
rather than its own course alone — with the caveat, spelled out under Known below, that the courses
only cover the table and furnace callers. The rest are inferred, not tested.

## The block scanner only ever saw half the world

Two defects in one method, found by reading it end to end after the counters stopped making sense.

**The chunk walk stepped only diagonally.** `rescan()` enqueued four neighbours: `(x±1, z±1)`. Every
one of those changes both coordinates, so `(x + z) % 2` never changes along any path — from the
player's chunk the walk reaches only chunks of the same parity, and the other half of the world is
never scanned at all. Not a shorter radius. A checkerboard. The cutoff cannot be blamed either:
`tick()` calls `rescan(MAX_VALUE, MAX_VALUE)`.

**A freshly-scanned chunk walled off everything behind it.** A chunk scanned under
`RESCAN_TICK_DELAY` ago hit `continue`, which skipped enqueueing its neighbours along with the scan.
`rescan()` runs about once a second against an 80-tick delay, so the ring at distance 3 is nearly
always too fresh: the walk stopped there.

The measurement names the second one exactly:

```
bs=241/241/13@50ms     241 passes, all completed, 13 chunks each
```

Thirteen is the Manhattan disk of radius 2 — `1 + 4 + 8`. `isPriorityChunk` is `getChunkDist <= 2`,
the only chunks exempt from the delay. The walk covered the exempt core and not one chunk more. That
was the bot's model of the world.

```
before   bs=…/13    reach 13 chunks
after    bs=…/157/31@143ms   157 walked, 31 re-scanned
```

Recency now skips the **work**, not the **traversal**. `scanChunk()` is gated exactly as before, so
this adds reach rather than scanning — the new counter reports chunks walked and chunks re-read
separately, because after this change they differ and the gap is the point.

Both scanner fixes stand on their own evidence. Thirteen chunks of reach is indefensible whatever
else was happening.

## Test results

```
craft_at_distant_table   PASS 6/6      (5 standalone + 1 inside the full suite)
craft   full suite        10 PASS  2 INVALID  0 gate failures
                          was 9 PASS / 3 INVALID on the same suite before the fix
nav     full suite        11 PASS   1 INVALID  1 gate failure
                          combined: 21 PASS, 3 INVALID, 1 gate failure over 24 courses
```

Every one of those 24 runs was at **9.7–10.0 fps** — roughly two thirds of the frame rate this bench
calls healthy. Green on starved hardware, not on a quiet host.

The craft INVALIDs are `chop_tree` and `mine_diamond`, both INVALID at the same ~10 fps before this
change, so the score moved 9 -> 10 with nothing traded for it. The single gate failure in the whole
sweep is `freezes == 1` on `nav_ladder` — on a run that reached its goal in 15.6 s at
`final_dist=1.0` with zero self-falls. One freeze at 10 fps is what the guard's first keyword exists
for.

Worth naming: `nav_wall2` passed here at 10.0 fps, and it is one of the two courses whose failure at
9.9–10.0 fps is the incident that motivated the starvation guard in the first place.

## Known, and worth reading

- **The blast radius of the interact fix is wider than the courses that cover it.**
  `InteractWithBlockTask` and `DoStuffInContainerTask` are also used by nether-portal construction,
  `ConstructGraveTask`, `ConstructIronGolemTask`, `PlaceSignTask`, `PutOutFireTask`,
  `CoverWithSandTask` and the storage-container tasks. **No course exercises any of those.** The
  craft ladder is the real gate here — it hits the table and furnace paths on every run — and the nav
  suite is a general regression check that may not touch the changed branch at all. Those other
  callers were standing still too, and are expected to be fixed by the same change; that expectation
  is untested and is written down as such rather than claimed.
- **The starvation guard prints the wrong diagnosis.** It says "host starved — Close whatever else is
  running" while the box can be 60% idle. The 14 fps floor itself is sound and measured: on this
  machine the client caps at 12 fps whatever is tried, and at 12 fps three runs reached no rung in
  five minutes while 15–18 fps reached wood in 21–43 seconds. It is the message that names the wrong
  cause, and it cost a session's worth of hunting through `docker stats` before anyone reread the
  reasoning sitting in the same file. Fix the wording, not the threshold.
  Worth knowing alongside it: the whole nav suite PASSES at 9.7–10.0 fps. The floor is calibrated on
  the craft ladder's long rungs (smelt, mine, fell a tree within a window), not on navigation, and a
  PASS is valid at any frame rate — the guard only ever downgrades a FAILURE. So "below 14 the bot
  cannot perform" is true of the rungs and false of the walking.
- **Clicks on empty slots in an open table** (`CLICK … cursor=empty target=empty`) appeared in the
  failing logs and not in the green ones. That may be a consequence of the same standing-still, or a
  separate defect. It is left open rather than assumed absolved.
- **Release tags have been pointing at stale source, and this is the first one that does not.**
  `build.gradle` sets `targetCommitish = "1.21.11"`, so GitHub creates the tag on that branch's head
  — while the work happens on `main`. The two had drifted by **717 commits**. The attached JAR is
  built from the working tree and so was always current; only the tag was wrong, which is why nobody
  noticed. If you checked out `v0.69.0`–`v0.71.0` to read the code behind these notes, you got source
  without the fixes they describe. The branch is fast-forwarded and the check is now part of
  `docs/RELEASE.md`.
- `gradlew build` does not deploy. `deploy/deploy_jar.sh` is a separate step, and skipping it made a
  fix look like it had made things worse — on a binary that did not contain the fix.
