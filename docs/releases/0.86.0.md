# 0.86.0 — the bot now collects what you sent it for

738 commits since 0.85.0. The headline is a class of bug rather than a single fix: the bot could be
sent for a resource, walk to it, stand next to it, and never pick it up. Several independent causes
all produced that one symptom, and they are fixed here.

Suites at release: **craft 22/22, nav 12/12**, playthrough (full-game run) 3/3.

---

## 1. It walked to the drop and did not take it — the tool gate

`MineAndCollectTask` disabled its own pickup path ("a separate task owns collecting") and then
returned "go and craft a pickaxe first" *before* that separate task could ever run. Until the tool
requirement was met there was no pickup path at all. A bot sent for a diamond 8 blocks away turned
off its own collecting and went looking for wood on a stone arena for the rest of the run.

A tool is needed to BREAK a block, not to walk over a drop.

**HOW TO TEST:**
```
;get diamond 1        # with a diamond already lying on the ground nearby
```
It should walk to the drop and collect it instead of leaving to craft a pickaxe.
Bench: `python deploy/runner/run_suite.py craft --only mine_diamond` (was 6/8, now 8/8).

## 2. It stood 1.5 blocks from its own coal for thirty seconds — the close-range walk

Every failure of `mine_coal` had the same shape once instrumented: the drop is ONE BLOCK DOWN in
the hole the bot just dug (0.7–2.5 blocks horizontally, dy = -1.0, without a single exception in 16
runs), and the body did not move AT ALL for the full 30-second navigation lock. Worst run: 0 of 3
coal, four dead locks, two minutes standing next to its own drop.

A dropped item is collected by TOUCHING it, so inside a couple of blocks the useful primitive is
the one a human uses — face it and hold forward. No route, no search, no lock. It runs only after
the progress checker says the body has stopped moving, so a healthy approach is untouched.

Measured, arms interleaved inside a single invocation: **off 4/8, on 7/8** (pooled with an earlier
series: off 9/14, on 12/14).

**HOW TO TEST:**
```
;get coal 3           # on a world where coal is in a wall or floor, so the drops fall into the hole
```
Watch what happens after it mines: it should step onto the drop rather than freeze beside it.
Bench: `run_suite.py craft --only mine_coal --repeat 10`.
Flag if you want to compare: `entityCloseRangeWalk` (now ON by default).

## 3. Navigation could give up permanently and leave the bot frozen

Three recovery paths, all off before this release:
- `entitySearchMustMove` — a search that has not moved the body for 6 s releases its lock instead of
  holding the bot still for the remaining 24;
- `barrenStreakPerEntity` — the "we got nowhere" counter is kept per target, so alternating between
  two unreachable drops can no longer reset it forever (it once reached 49 dead locks in one run);
- `entityWanderWhenNavRefuses` — when navigation refuses outright, wander instead of returning
  "navigation has it" every tick with nothing running.

Full-game playthrough with these on: **3/3 against 1/3**, interleaved, in one session.

**HOW TO TEST:** `;gamer` and watch it reach stone tools; it should no longer park motionless for
minutes at a time. Bench: `python deploy/runner/gamer_smoke.py`.

## 4. mine_stone built a tower into the sky instead of finishing

Tungsten keeps one module-global "where am I walking to", initialised to a point at y=10 from the
days of hand-driving. The bot's own task system never writes it, so it sat there holding "go up" —
and every time a mining segment finished, the resume routine aimed the navigator at it. From the
bottom of a fresh hole, the only way toward y=10 is up. The bot mined its eight cobblestone in 29
seconds and then spent the rest of the run climbing.

**HOW TO TEST:** `;get cobblestone 8` standing on a stone floor. It should stop when it has them.

## 5. Faster block scanning

The nearest-block scan ran its expensive validity tests before the cheap distance rejection.
Reordered to test distance first — same answer (verified by an audit mode that computed BOTH orders
and compared: zero mismatches), a fraction of the work.

**HOW TO TEST:** nothing to do; it is a speed change. `scanCheapTestFirst` if you want it off.

## 6. Bench and stand fixes (for anyone running the test suite)

- The stand deploy now REFUSES to ship a jar older than the compiled bytecode. `gradlew
  compileJava` makes classes and no jar, so compile-then-deploy used to silently test whatever jar
  was lying there — that cost a ten-run batch measured against code that was never loaded.
- GPU is attempted and, if a client cannot come up on it, the deploy retreats to CPU by itself. The
  py4j wait is now bounded; it used to be an infinite loop, so the first failure hung the deploy
  forever. On WSL2 hosts with no `/dev/dri` the GPU path cannot work at all — documented in
  `docs/AUTOTESTING.md` — and this makes that harmless instead of fatal.

## Known bugs

- The full-game playthrough reaches STONE TOOLS and no further. It no longer fails on machine speed;
  it fails on the bot. There is not one wall but a family of them — four captured runs hit four
  different ones. The only thing they share is an enormous block scan (95k–1.35M candidates against
  200–400 on a passing course); whether that is cause or merely what a nine-minute survival run
  looks like is NOT established.
- `mine_coal` is 7/8, not 8/8. One contradiction in the close-range walk is unexplained: the aim
  snap survives the tick 240 times in 241, yet the aim reads correct on only a fraction of ticks.
  The suspect is target thrash between multiple drops; it is under measurement.
- The pvp suite does not record FPS at all, which means seven load-tolerance flags on pvp gates are
  currently inert. Proven from the condition, not from a run.
