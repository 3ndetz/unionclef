# 0.86.0 — the last red rung goes green, and it was a debug constant

`mine_stone` was the only failing course on the craft ladder and had been for days. Both suites now
run clean: **craft 12/12, nav 12/12**, zero invalid on either.

## What was broken

The bot mined its eight cobblestone in 29 seconds — it was never a mining problem — and then spent
the whole haul building a tower into the sky and stood on it until the clock ran out. The course
reads the pack at the end, so a run that met its target in half a minute scored zero.

Tungsten keeps one module-global "where am I walking to", and it is *initialised* to a point at
y=10, left over from when the mod was driven by hand. Only `;goto`, a keybinding and a couple of
manual primitives ever write it; the bot's own task system never does, because it steers the
navigator directly. So through an entire run it sits there holding "go up".

And every time a mining segment finished, a resume routine read it and aimed the navigator at it:

```
[Tungsten] Mining done - passage open
MovementQueue: 9 movement(s) 0,-63,0 -> 0,-54,0 CLIMB+9 for goal=(0.5,10.0,0.5)
```

From the bottom of the hole it had just dug, the only way toward y=10 is up.

## What it gave

Both arms, with the order swapped between pairs so the winner could not follow the position:

```
control:  n=10  mean 5.70  sd 3.97  pass 6/10   towered 3/10
fixed:    n=10  mean 9.00  sd 0.00  pass 10/10  towered 0/10
```

Ten runs, ten passes, standard deviation **zero**. The pre-registered mechanism gate — a tower left
standing in the world afterwards — went 3/10 to 0/10.

## Also in

- **One navigation teardown instead of three.** `;stop` stopped the movement queue but not the
  navigator, which handed it a fresh leg a tick later; the disconnect reset stopped six tasks and
  neither of those two; and altoclef's task layer could not reach any of it. A task ending now stops
  the route with it — a search still in flight used to land two seconds late and drive a bot that had
  no goal.
- **A failed break no longer bans a hundred-block cube.** One refusal used to ban 101×101×101 around
  the bot. On the survival world that measured `breakFail=2` against `cbAvoid=842,176` — two failures,
  and 842 thousand blocks the bot was no longer allowed to touch. It now bans the block, and widens to
  a region only when three distinct refusals agree, which on genuinely protected land takes seconds.
- **A 30-second navigation lock that got nowhere now counts as a failure.** The limit meant to stop it
  counted exceptions only, so it never once saw the failure it was written for.

## Known bugs

- The playthrough ladder reaches **stone tools** and stops there. The wall in daylight is the break
  ban above; whether fixing it carries the ladder past coal is **not yet measured**.
- The bot **stalls hard after the stone rung** — motionless at one position for 70-90 seconds with
  every drive counter flat at zero (`pdEnter+0`, `dbTick+0`), then resumes on its own. Seen in both
  measured runs. Not diagnosed yet; the drive is not merely failing to route, it is not being
  ticked at all, which is a different question from the ones answered here.
- `mob_trio` fails its "zero damage while fighting three mobs" gate. Checked with the new fixes
  pinned off: it fails the same way, so it is not a regression from this release.
- `bow_flee` / `bow_flee_hard` remain red for reasons of their own.
- `mine_diamond` measures 5 passes in 6. A course at that rate still fails about one sweep in six.

## The playthrough is measurable again, and the bench was the reason it was not

Acceptance criterion #1 spent a week reporting "the machine cannot answer today" — 7.0 fps against
a floor of 12. The machine could answer; the bench was standing on its own foot. The playthrough
uses `tester1` only, and `tester2` sits on the flat arena doing nothing while still burning ~110%
of a core, because an idle Minecraft client is not an idle process — it renders.

```
both clients up     7.0 fps  ->  INVALID, refused before the run even starts
tester2 stopped    11.0 fps  ->  PASS, wood tools@185.4s
tester2 stopped    10.0 fps  ->  PASS, STONE TOOLS@184.6s
```

`gamer_smoke` now stops the clients a run does not use and puts them back in a `finally`, so this
is not something anyone has to remember. Worth saying plainly what it was *not*: it was not the
GPU. That was chased to the end first and cannot work on this host at all — the container has no
`/dev/dri`, only `/dev/dxg`, and no Mesa path builds a screen without DRM. The GPU work's value is
the fallback it left behind: the deploy now tries the GPU, checks whether a client actually came
up, and puts the bench back on the CPU by itself when one did not. See `docs/AUTOTESTING.md`.

## How to test it

```
python deploy/runner/run_suite.py craft      # expect 12/12
python deploy/runner/run_suite.py nav        # expect 12/12
python deploy/runner/gamer_smoke.py          # the playthrough; quiets the box itself now
python deploy/runner/diag_pit.py             # per-second trace + the world afterwards
python deploy/runner/diag_pit.py coal        # same, for the coal rung
```

`mine_stone`'s verdict now prints `dug=N/4 of the spawn column, tower=N high`, read out of the world
after the run. That is a yes/no fact with no spread, and it exists because the gate metric could not
carry a claim: an inert flag was measured moving this course's mean by 6.25 cobblestone.
