# 0.95.9 — G106 for real (0.95.8 shipped it stale)

0.95.8 was built with the G106 food change **missing from the jar**. A stale IntelliJ
`versions/1.21.11/bin/main` compile output (foodUnits still 220) was picked up by the remap
pipeline, so the released 0.95.8 jar still had `foodUnits = 220` even though the source, the
preprocessed source, and the shadowJar all had 140. `gradle clean` and `--no-build-cache` do
not touch `bin/`, which is why it slipped through. 0.95.9 is built after `rm -rf versions/*/bin`
and the jar is verified to contain `foodUnits = 140` (javap on the class inside the jar).

If you pulled 0.95.8 for the food change, use 0.95.9 — 0.95.8's food behaviour is the old 220.

---

## The fix (G106), now actually in the jar

- **Hay multiplier 50 -> 7.** A hay bale within 75 blocks multiplied the WHOLE food goal by 50
  (priority ~1293 near a village), burying diamond/nether-prep tasks (15-40). A hay bale is worth
  ~7 animal kills of food, not 30.
- **foodUnits 220 -> 140 (minFoodUnits 120).** The nether departure is gated behind the food goal
  (the main loop only falls through to "Going to Nether" when every gather is satisfied). 220
  units (~27 cooked meats) gathered up front kept a probe in overworld prep for 25 minutes. 140
  (~17 meats) still carries a nether trip; the bot re-collects below the target and the
  emergency-food path ramps to infinity when actually low, so a smaller buffer is topped up.

  ⛔ **foodUnits is a CONFIG value, read from `configs/beat_minecraft.json` at runtime — the class
  default only applies to a FRESH config.** If you have run the bot before, that file already has
  `foodUnits: 220` and it OVERRIDES the new default; edit it to `140` (and `minFoodUnits` to `120`)
  or delete the file to regenerate it. The hay-multiplier change is code, not config, so it takes
  effect for everyone as soon as the jar is in place. (This override is also why 0.95.8's stale jar
  hid the problem twice: even a correct jar shows the old 220 until the JSON is updated.)

## HOW TO TEST

`python deploy/runner/gamer_smoke.py 12 --from cp0918-1030-t494 --daylock --record` — the food goal
should read **"Collect 140.0 units of food"** (not 220), food/hp stay healthy (no starvation), and
the bot progresses (deep mining, nether prep). Verify the jar itself before trusting a run:
`javap -p -c` the `BeatMinecraftConfig` class inside the jar should show `sipush 140`.

## Verification status

The jar is verified to CONTAIN the change (the thing 0.95.8 got wrong): `javap -p -c` on the
classes inside `unionclef-1.21.11-0.95.9.jar` shows `sipush 140` (foodUnits) and `double 7.0d`
(hay multiplier, no more 50.0). The stand's `beat_minecraft.json` is set to 140. The full runtime
re-run (reaches "Going to Nether" faster, no starvation over a window) was blocked by the
gamer-server crashing on the contended stand and is pending stand recovery. Risk of the foodUnits
cut is low: 140 is ~17 cooked meats, the bot re-collects below it, and `needsEmergencyFood` ramps
to +inf when actually low.

## Known, not fixed

- The night track (death = base loss) stays deferred by the operator; a daytime death (respawn =
  base loss) was also seen on the stale build and is recorded for the next pass.
