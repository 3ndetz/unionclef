## The bot was not being out-fought, it was being out-ticked

Every mutual duel runs this mod on **both** sides, so every counter the bot exposes is also running
on its opponent. `gateStats` and `punkStats` have been on the py4j surface the whole time and no
probe had ever read the victim's copy. Reading it took one line and settled `allround` immediately:

| | bot | victim |
|---|---|---|
| `punk` task called | 201–396 | **1375–1404** |
| combat ticks | 221–287 | **417–475** |
| swings passed | 24–29 | **39–43** |

The bot's combat engine was ticked **three to seven times less often** than its opponent's. Not aim,
not reach, not the trade — it simply got a fraction of the decisions.

The cause was one line in the course drive: `punkStop` before every arrow. And the drive had no
choice, because two writers on `WindMouseRotation` in a tick means last-writer-wins, so a shot taken
while the pursuit was live never converged and the arrow was loosed wild or timed out.

**Fixed in the engine rather than worked around in the course.** `CombatController` now yields the
camera while `BowShooter.isAimCritical()` — the contract `PathExecutor` has honoured for a while —
and **keeps producing movement keys**. Walking at someone and aiming at them want the same yaw; only
the ballistic pitch differs, so the composition was always available and only the arbitration was
missing.

Three runs at 27.9–29.0 fps, against five before it:

| | before | after |
|---|---|---|
| melee swings landed | 22–25 | **31–34** |
| crits | 5–10 | **14–17** |
| share of combat ticks | 0.48–0.69 | **0.80–0.88** |
| margin | mean −4 | −2, −2, −2 |

It also closed a crit gap nobody had attributed correctly. Crits per passed swing went bot
`0.46/0.34/0.31` against victim `0.58/0.54/0.60` **before**, and bot `0.52/0.50/0.50` against
`0.50/0.32/0.41` **after**. A bot standing still to shoot does not bunny-hop, so it swung
flat-footed. `bowYield` counts the handed-over ticks: 15, 26, 0 on the bot, 0 on the victim, and 0
by construction on every sword-only course — which is the blast radius.

**The course is still red and this does not pretend otherwise.** It is the first change to move it,
and it moved the mechanism and the outcome together.

### Three suspects for the remainder, all dead, all by control runs

Written down at the site so no future pass re-derives them:

- **The ranged phase.** `MELEE_AT` raised to 999 so the drive never enters it: `6:8, 6:9, 6:8, 6:8`.
  Indistinguishable from `−2, −2, −2` with the bow phase live. Deleting the bow economy entirely
  changes nothing.
- **The wounded kite.** This is the one pvp kit with a bow, so `hasRangedOption` is true and the
  low-health branch actually fires here — `lowHp` reads 56/0 and 75/0 against 0/xx everywhere else.
  Arrows removed so the predicate declines (`lowHp 0/49, 0/68, 0/54` confirms): `6:8, 5:7, 6:9`.
  Unchanged.
- **The crit rate**, above — already closed by the arbiter. The first version of that note quoted
  `critWindowSwings` as a range across **both builds**, which hid the fact entirely and would have
  cost a fourth investigation. Corrected.

## Two red gates are asking a level fight to be won

The duels pin the victim to `combatReachControl=false` and punk both sides with the same controller
and kit. That is what finally let the setting be measured — and it also fixes what the gate can mean.
`kills >= deaths` between two near-identical fighters is a coin flip with ties passing.

| course | margin, bot with the flag vs the same engine without it |
|---|---|
| `melee_basic` | **0** (n=7, sd 0.75) |
| `edge_duel` | **−0.27** (n=11, after 0.77.0's stand-off fix; −3.82 before it) |
| `allround` | **−2** (n=3, after the arbiter; about −4 before it) |

`narrow_bridge_duel` is the same story read with a better instrument: five healthy runs give margins
`−6, +2, +2, −3, +3` and a blow ratio of **1.05 ± 0.13**. That course was chased through four
investigations — collision counters, rim time, levelling the sides, the bowless retreat — and every
effect came out smaller than its own spread **because the effect is zero**. The series scored 4 of 6,
which is what a level fight produces against that gate.

The consequence worth stating: a combat change landing **outside** the flag cannot move those gates,
because the opponent gets it too and the margin returns to zero by construction. A future pass should
target the flag itself — make the cooldown behaviour beat parking at strike distance, or conclude it
cannot and remove it.

## The rule that distrusts the fast planner, measured for the first time

`PathFinder` accepts a fast route only when it is complete, citing the toggle: *"proven with the
toggle: OFF passes, ON fails"*. Three arms, three runs each, all at a healthy frame rate:

| arm | `nav_slime` | `nav_ladder` | `nav_water` |
|---|---|---|---|
| `fastBlockFirst=false` (the old behaviour) | 0/3 | 3/3 | **0/3** |
| default (fast-first + complete-only) | 2/3 | 3/3 | **3/3** |
| `fastGuidePartial=true` (rule relaxed) | 3/3 | 3/3 | **0/3** |

The quoted sentence is now exactly backwards — OFF fails `nav_water` outright — because
`FastPlanner.special()` models ladders, swimming and slime bounce today. But the rule itself **earns
its keep on `nav_water`**, where relaxing it costs 3/3.

A conditional version was then built and reverted: reject a partial route only when the remainder
crosses fluid, on a straight walk from the route's end to the goal. It scored 6/9 with `nav_water`
at 0/3 — identical to relaxing the rule outright, so the discriminator never fires on the course it
was written for. The next attempt should **ask `FastPlanner` which move it lacked** — it knows why it
stopped — rather than infer it from geometry, which is what that was. Default unchanged (8/9 against
6/9 for both relaxations); `fastGuidePartial` ships OFF as the instrument that produced the table.

One correction: a note claimed the rule "costs `nav_slime` a run in three" off a single 2/3 series.
The revert verification read 3/3, so slime is 5/6 against 6/6 — which no series this size separates.

## G-0b: six reads of a foreign object model for a list altoclef itself produces

`acceptableThrowawayItems` is derived from altoclef's own settings and pushed into the pathfinder so
it can plan placements. Six places then read it back **out** of that object — altoclef depending on
baritone's type for data altoclef created.

The write stays; the reads take `AltoClef.getThrowawayItems()`, a snapshot of the **union** of the
shipped defaults and ours, captured at the one moment both halves are present. Union matters: reading
only the altoclef half would have quietly narrowed what the bot is willing to place. A seventh,
commented-out read went with them.

**Tested:** craft suite, 0 gate failures, 11/12 — identical to the pre-port baseline. `craft_table`
covers the `PlaceBlockTask` reads at 30.0 fps; `escape_lava` covers `EscapeFromLavaTask`'s, though
that one passed at 10 fps and is marked.
