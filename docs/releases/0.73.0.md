## The End had never been tested, and the excuse for that was two rcon commands old

Beating the game happens in the End. No suite touched End content at all, so four things sat
permanently unverifiable — `GetToOuterEndIslandsTask`, `KillEnderDragonTask`, `DragonBreathTracker`,
and `GoalAnd`, whose only surviving user was `GetToOuterEndIslandsTask.makeGoal`. Every proposal to
touch any of them was parked on the same sentence: End content cannot be checked.

It could. This is the whole investigation that overturned it:

```
execute in minecraft:the_end run time query daytime   ->  The time is 1000
execute in minecraft:the_end run forceload add 0 0    ->  Marked chunk [0, 0]
```

There are now three End courses.

```
end_walk      PASS 5/5   32 blocks of end_stone, ~10s
end_gateway   PASS 3/3   26 blocks to an end gateway
end_dragon    info       recorded every run, gates nothing — see Known
```

They build their own platform with `execute in minecraft:the_end run …` rather than teaching
`Arena` about dimensions. `Arena` is shared by 24 passing courses, and adding a concept to it to
support one new test is how a green suite acquires a new way to fail.

## The gateway approach arrived one run in three

`GetToOuterEndIslandsTask` steers with `getCustomGoalProcess().setGoal(goal)` + `.path()` — the same
legacy hand-off whose removal left the bot standing still in 0.72.0. Here it was not dead but
**unreliable**, which is harder to catch: a task that works one time in three reads as bad luck.

```
before (legacy engine)   closest = 2.2 / 7.7 / 12.3      1 of 3
after  (live drive)      closest = 1.0 / 1.2 / 1.2       3 of 3
```

The goal it built was `GoalAnd(GoalComposite(eight cells beside the gateway), GoalYLevel(74))` —
"stand on one of these eight AND be at y=74". Beside, not on: you stand next to a gateway and throw
the pearl in, because stepping into one teleports you. Said plainly that is "walk to the nearest of
eight cells", which the live drive steers at directly. The goal type in the middle was never
carrying an algorithm.

**The y=74 term is dropped, and that is a bug fix rather than a simplification.** It is a hardcoded
real-End gateway height, while the eight cells already sit at `gateway.y-1`. For a gateway at any
other height the AND could never be satisfied at all.

That removed the last user of `GoalAnd`, and the class is **deleted** — confirmed by the build, not
by a grep, because a grep is exactly what got this wrong on a previous attempt.

## The bot could not say which world it was in

`getGameState` had no dimension field. Nothing over py4j could answer "am I in the overworld, the
nether, or the End", and the first End course had to infer it from the bot standing at y=65 where
the overworld arena has only air — the precise sort of guess a primitive exists to remove. A
playthrough crosses two portals and needs this constantly. Added as `getGameState.self.dimension`.

## Known, and worth reading

- **`end_dragon` is `info`, not a gate, and that is about the arena rather than the bot.** First
  dragon measurement ever taken here: `200.0 -> 200.0`, zero damage in four minutes, with beds,
  obsidian, a bow, 64 arrows and a sword in the pack. The log says why — `"Failed to place,
  wandering timeout."`, and movement chains dropped after `body has not left … for 121 ticks`. Both
  strategies wait on the dragon **perching** (`Mode.WAITING_FOR_PERCH`; the bed trick needs it too),
  and a dragon summoned into a world with no `EnderDragonFight` never perches. Building the bedrock
  podium the task looks for was necessary and not sufficient. A real dragon course needs a genuinely
  generated End entered through a real portal — a world-setup problem, not a course problem.
- **What is left of G-0 here is porting, not tidying.** Nine files import baritone's `Goal`; eight
  uses are live and the single dead import is gone. The three `RunAway*` tasks are the obvious next
  targets and were deliberately not taken: `GoalRunAwayFromEntities` reads entity positions live
  while `AltoGoal.Flee` snapshots them, which is a behaviour change on the combat path with no fresh
  mob baseline behind it.
- **`@gamer` is unmeasurable on this hardware.** Its own guard stops it at 5.0 fps against a floor of
  12. The box is 53% used with 47% idle while the client alone takes 383% to produce those 5 fps — a
  single-threaded render ceiling on a live survival world, where the same client manages 10 on the
  flat arena. A stand limit, not a bot defect.
