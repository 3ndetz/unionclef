# 0.90.0 — the grid stopped cutting corners

## What was wrong

The bot could freeze for a whole run, on ordinary terrain, and nothing would rescue it.

The route producer that drives the playthrough — `CombatPathfinder`'s grid BFS — offered
diagonal steps without checking the two cells the body has to pass **between**. It only asked
whether the destination was walkable. So it routed a diagonal through a notch with solid blocks
on both sides: a step this game cannot make.

The blocks at the spot this was traced to, read rather than guessed:

```
(85,125,-55)  grass_block   solid
(84,125,-54)  dirt          solid
```

Both full, with the diagonal between them handed over as a route.

## Why one impossible step cost the whole run

`MovementQueue` accepts the diagonal. `MovementDiagonal` cannot execute it and holds forward at
zero velocity. And while a chain is *running*, the tick belongs to it alone — so nothing else
runs either: not the walker, not the build primitives, not the physics executor. Meanwhile the
navigator counts "a chain is running" as "work is happening" and never replans.

Measured on a five-minute run: 64 chains started, 9 steps taken, zero of 12 target blocks
reached, no ladder rungs at all. The walker ticked 36 times in 45 seconds and was idle on every
one of them.

`FastPlanner`, the other route producer, has always refused corner cuts. This release makes the
two agree.

## Measurements

| suite | with the fix | baseline, same build |
|---|---|---|
| nav | 14/14 | 14/14 |
| craft | 22/22 | 22/22 |
| pvp | **11/12** | 10/12 |

`edge_duel` passes now; it was one of the red courses. `chase_terrain` is the remaining pvp
failure and was already red before this.

On a repro of the stall, arms interleaved: the control wedged in 2 runs of 3, the fix in 0 of 3,
with three to ten times as many movement steps.

## Also in this release

- **The bench was not resetting its counters.** `gamer_smoke` called a method that rewrites three
  server dictionary entries and zeroes nothing, so every playthrough counter was a total since
  the client launched. Ten queue counters were missing from the reset as well. Fixed in both
  runners; several earlier readings had to be retracted as *unmeasured* rather than wrong.
- **The stall repro was measuring the wrong world.** It only connected to the gamer server when
  the client was in no world at all — and after a suite run it is always in one, the flat test
  arena. Now it connects unconditionally and verifies by teleporting and reading the position
  back.
- **`nav_notch`**, a new course: a diagonal whose two corner columns are solid, with an open lane
  one row over. It is labelled honestly as a guard — it does not reproduce the historical stall,
  because the trigger is in the route rather than in the terrain.
- **`repro_stall.py --restore`** rebuilds the cells a terrain test depends on. The bot had mined
  the original notch out of existence, after which the stall stopped reproducing in both arms and
  looked exactly like a fix.

## How to try it

```
;settings gridBfsRefusesCornerCut     # on by default now; set false to compare
```

Watch `gridCorner` in the counters: it climbs into the hundreds of thousands on real terrain,
which is how often the grid was previously willing to squeeze past a corner.
