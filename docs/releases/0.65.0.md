# 0.65.0 — the bot stopped building with cheats

Block placement was bypassing the game. The packet asserted a click on a face the
camera never reached, and nothing capped the speed — up to 96 blocks **inside a single
tick**. That was the clip where six panes of glass appeared at once.

Now a block is placed through the game's own raytrace, aiming at a face, once every 4
ticks — the same law as a held right-click. In the process the builder learned to
**walk** and **build a column by jumping**, and breaking learned to **approach** what it
is breaking.

| check | before | after |
|---|---|---|
| navigation trace (`nav`) | 12/12 | **12/12**, zero gate refusals |
| build (`diag_build`) | 1 cell out of 4 | **12 runs out of 12** |
| break+replace (`diag_replace`) | 1 of 3 | **12 of 12** |
| `bridgeForward` bridge, flat | 0 cells out of 6 | **6/6**, 5 runs out of 5 |
| bridge over a 10-block void | fell into the void | **18 blocks, the bot crossed** |
| fake placements | 4 spots in the code | **0** |

## The main thing: half of the condition

Upstream requires `canPlaceAgainst(neighbour) && placementPlausible(cell)`. The second
half asks whether the future block would intersect anyone's hitbox — **including its
own**. Only the first half had been ported, so the bot would walk right up to a wall and
try to place a block into itself, forever.

After that a full adversarial audit of the whole port against baritone was run: **18
discrepancies, 8 causes, all closed**. The nastiest one — `canPlaceAgainst` existed in
two copies: the correct port lived in `MovementHelperB`, and right next to it lived my
own weaker duplicate, which let a shulker box through. Clicking one **opens a chest**,
and the queue counted a block that does not exist.

## Two core bugs found along the way

**The navigator's arrival check was a radius-2 sphere in 3D.** A goal one block up was
counted as reached — the bot switched off **without moving**. This exact bug had already
been found and fixed in the same file one line below, for feeding goals, with a comment
saying "must not go up". The main check was left untouched.

**The navigator had no "stand EXACTLY here" goal** — only "get roughly there". The
builder needs the second kind: it picks a cell precisely because that cell has line of
sight to the face. In baritone this is `GoalBlock`; it has been ported.

## Trust the world, not the report

The last two defects are one lesson. `//replace` was losing cells that the break phase
had not gotten to yet, and reporting success. And the queue counted a cell as placed
based on `ActionResult.SUCCESS` — but that is a **client-side prediction**, and the
server can reject it: `placed=3`, while the cells are still empty ten seconds later. Now
state is read from the world: not filled means the work still needs doing.

## How to test

```
;settings verboseDebugLogging true      # per-tick build and bridge traces
//set stone                             # build queue, poll buildQueue()
//replace stone glass                   # break + place, an honest cycle
```
Agent levers: `buildQueue()` (queue, refusal reasons), `setBuilderWalks(false)`
(hand movement to the agent), `placeStats` (gate counters).

## Known limitations

- The build places what is reachable, and **honestly hands back the rest** via
  `buildQueue().deferred` — a cell whose every neighbour is sealed off by a block just
  placed cannot be placed from the current position. The walking half of
  `BuilderProcess` has been ported, scaffold placement has not.
- A bot that fell into the void **does not recover on its own** (the client imposes its
  own position on the server); the bench now lifts it back up itself, but the mod itself
  has no such safeguard.
- `chase_terrain` is still red — untouched in this release.
