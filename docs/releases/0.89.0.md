# 0.89.0 — the bot stops standing still for a fifth of the run

## Aiming at air was counted as mining progress

One test in `MovementProgressChecker` decided "did we make progress?" by asking whether the block
we were breaking is air now. It checked that against a cell recorded on the previous tick — so a
cell that was **already** air, which is exactly what aiming at nothing looks like, passed on every
single tick and reset the stall detector for ever. And while "breaking", the distance check is not
consulted at all, so a motionless bot could not fail either way.

That one line guards both the wander task and the block-destroy task, which is why the bot could
stand in one spot for minutes without anything ever giving up:

```
before   wanderChk=4406/0   wanderFail=0     4406 ticks, 10.6 blocks travelled, never "stuck"
after    wanderChk=1508/8   wanderFail=8     the detector fires and the task hands control back
```

Air now counts as a break only if the block was solid when we aimed at it.

**Measured over 17 paired playthrough runs** (both arms started on the same ground, so terrain
cannot explain the difference):

| | effect | verdict |
|---|---|---|
| time spent standing still | **−73.6 s per run** | established (t = −2.16) |
| share of the run standing still | **−20.9 %** | established (t = −2.13) |
| ladder rungs reached | +1.06 | directional, **not** established |

Read that honestly: the bot gets about a fifth of every run back. It does not follow that it
climbs further — removing a stall returns the time, it does not say what to do with it.

**HOW TO TEST.** Run the playthrough and watch whether the bot ever freezes in place:

```
python deploy/runner/gamer_smoke.py 6
python deploy/runner/stall_corpus.py <the log>     # lists every stall episode it found
```

`stall_corpus.py` splits them into CHURN (counters running, body still) and DEAD (nothing ticks
at all) because they need opposite fixes. In game, `@stats` carries `wanderChk=ok/tripped`,
`wanderFail` and `airProg`; if `wanderChk` shows thousands of "ok" and zero trips while the bot
is not moving, this bug is back. Turn it off with `@tungsten stallCheckNeedsMovement false`.

## Bench

- **`paired_ab.py`** scores a paired A/B: it pairs arms by the ground they actually ran on,
  reports rungs *and* stall seconds *and* stall share, excludes pairs where one arm barely ran,
  and says plainly when a result is not established.
- **`stall_corpus.py`** turns any playthrough log into a stall corpus, and flags coordinates that
  stall more than once — those are deterministic and fixable without statistics.
- `gamer_smoke` now pairs A/B arms on the same resolved spawn. Previously arms alternated by run
  index while the start walked 300 blocks along a spiral each run, so **arm A always got the even
  spiral points and arm B the odd ones** — two different sets of terrain, permanently. Any
  playthrough flag result taken before this should be treated as unmeasured, not refuted.
- `--pin-base` for non-boolean A/B values, and `--swap-alt` to swap the two containers' roles
  (it tells a code asymmetry from a stand asymmetry on mirror courses).

## Known bugs

- The playthrough still tops out around stone tools.
- `chase_terrain`, `mob_trio` and `mob_skeleton` fail; all predate this release.
- ~11 hits a run land for exactly 1.0 hp in pvp; the cause is understood (the server resolves a
  swing with the item it still holds) and removing it measured no damage gain.
