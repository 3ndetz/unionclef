# 0.62.0 — combat: one key writer, no dead band, reach that matches the attack gate

A full audit of tungsten (`docs/ai/audit-2026-07-27-tungsten-full.md`, 7 readers + 7 adversarial
verifiers, 88 verified findings) and the first fix pass off the back of it. The combat result is
the headline: the "стоит и смотрит, почти не двигается когда цель рядом" symptom was three
concrete code defects, not tuning.

## Combat (the "stands still" root, fixed)

- **The dead band.** `CombatController.combatMove` pressed forward only at `dist > 3.4` and back
  only at `dist < 2.0`, both **centre-to-centre**. Between them — i.e. exactly melee range — it
  pressed *nothing*. The only remaining motion, the circle-strafe, was suppressed near a drop by
  setting **both** strafe keys false, so on a ledge or a 1-wide bridge the bot pressed literally
  nothing and stood there.
- **It parked outside its own reach.** 3.4 centre-to-centre is ~3.1 eye-to-hitbox, while
  `TriggerBot` fires at 3.0 eye-to-hitbox — the chosen hold distance made a hit impossible. The
  correct threshold was already implemented in `SafetySystem`; `combatMove` overwrote it.
  `TriggerBot.REACH` is now public and the single source of truth, with `eyeToHitbox()` as the
  shared metric and `STRIKE_DISTANCE` derived from it, so the two can never drift apart again.
- **Two key writers at two different frequencies.** `SafetySystem.renderUpdate` (per RENDER FRAME)
  and `combatMove` (per CLIENT TICK) both wrote the same `KeyBinding`s, so which one won depended
  on framerate — the real reason stand results never matched live behaviour — and the per-tick
  writer bypassed the `VoidGuard` clamp entirely.

**New `CombatMoveIntent`**: producers *request* movement, `CombatController` resolves by priority
(safety first, close-quarters otherwise), `VoidGuard.apply` vetoes the result, and the keys are
written **exactly once per tick**. Anything not requested is released by construction.

Every direction is edge-tested **individually** before it is pressed. `VoidGuard` is still the final
veto, but it cancels all steering at once, so leaning on it alone turns "one unsafe component" into
"no movement" — which is how the bot froze on a ledge. Backing off is the dangerous direction (the
target stands on floor, so forward is nearly always safe), and the close-quarters pulse is now
forward-only and tested, instead of a naive forward/back jitter that walked the bot off a platform.

## `TungstenHelper` was dead code (C1.1)

`initReflection()` looked up `PathFinder.searchTimeoutMs`, a field that had moved to
`TungstenConfig`. The resulting `NoSuchFieldException` left `reflectionReady = false` **permanently**,
so `isTungstenLoaded()` always returned false and `tryPathTo` / `tryPathToEntity` / `stop` /
`isActive` / `isLocked` were permanent no-ops — the whole documented "tungsten as a fallback when the
primary pathfinder fails" layer had never executed. The reflection is gone entirely (the class
already referenced `kaptainwutax.tungsten.task.*` directly, so it protected nothing); a signature
change is now a compile error instead of a silently vanishing feature.

## Test harness (without these, no honest numbers)

- **k/d baseline.** Kills/deaths were read straight off scoreboard objectives using the
  `playerKillCount` / `deathCount` **criteria**, which Minecraft re-syncs from the player's
  *persistent statistics* — `scoreboard players set 0` is undone on the next stat change. A clean run
  inherited every past kill and death: `early_stop: kills() >= 1` fired on the **first sample** and a
  run "won" 1-1 before the bots had closed. Now reported as deltas from a baseline latched at start.
- **UTF-8 artifacts.** Writers used the platform default encoding, so on Windows (cp1251) the run
  died with `UnicodeEncodeError` *after* the scenario had already succeeded.
- **`--no-early-stop`.** An objective reached in the first seconds produced a 4-second clip and far
  too few samples to judge movement from.
- **`tg_send.py`** — uploads stand clips to the operator's Telegram. A text verdict is exactly the
  kind of self-reported claim that has been wrong before; the clip is the evidence.
- **compose**: host ports are overridable (`UCTEST_MCP_PORT` / `UCTEST_VNC_PORT`) — a dev box already
  running a real MC client holds the in-mod MCP port and the stand must not fight it for the binding.

`edge_duel` / `narrow_bridge_duel` are duels between two identical bots, so a ~1:1 trade is expected;
the bar is winning the exchange and not falling off by yourself.

## Known bugs / not in this release

The audit's structural findings are recorded as a **CRITICAL REGISTER (C0–C8, 60+ entries with
file:line) in `TODOS.md`** and are NOT fixed here:

- **Block-space search has no g-cost accumulation** — `updateNode` uses `child.cost + 1` and the
  `BlockNode` constructor discards its `cost` argument, so mining/bridge/`ActionCosts` prices are
  decorative and the search is greedy best-first on the heuristic alone.
- **Move generation is an either/or where neither branch is complete**: `smartMoves = false`
  (default) gives ~1086 children per expansion but has break+place; `smartMoves = true` gives ≤8
  clean children but **no break, no place, no ladders, no water, no diagonals** — `getChildren`
  returns early and never reaches `shouldRemoveNode`, where both plan hooks live.
- **Break is one cardinal same-Y cell** — no dig-down, no dig-up. `planPlaceMoves` still ships OFF.
- Combat still has **no health logic and never raises the shield autonomously**; aim and the stage
  machine still run per render frame with no delta-time term.
- `baritone/` is **not compiled** (`// include(":baritone")` in `settings.gradle.kts`); the live
  pathfinder is `shredder/`, in the same `baritone.*` package.
