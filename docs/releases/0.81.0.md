## Approaching an entity had no mover, so reaching one was luck

`GetToEntityTask` is what walks the bot to a mob, a player or a dropped item. On its normal path it
set a debug string and returned `null` — **issuing no movement at all**.

The G-0 pass had deleted the baritone call that used to drive the approach, leaving a note that the
real driver is *"the `tryPathToEntity` call below, on the progress-checker path"*. That path only runs
**after** progress has already stalled. So whether the bot ever reached anything depended on some
other task having left a path running.

`mine_diamond` is what exposed it, and the evidence is one line repeated six times. Across every run,
**every** route tungsten ever planned ended at exactly `(3, −60, 0)` — the standing cell beside the
ore at x=4, i.e. the *mining* approach. Not one route was ever planned to a dropped item. The bot
mined all three ores, the drops landed 1.9 blocks away at y=−61, and nothing moved it those two
blocks:

| drop | closest the bot ever came |
|---|---|
| (4.88, 0.88) | **1.35 blocks** |
| (6.78, 0.35) | 2.45 blocks |
| (8.82, 0.13) | 3.57 blocks |

Three ores out of three, every run, for the whole 300 s.

The fix asks for the path on the normal path too. `tryPathToEntity`'s own guards — a cooldown, a fail
counter and a retarget interval — already make that cheap and idempotent, and the branches above it
return early while tungsten is busy.

**Measured:**

```
diamonds collected   0 in every run before, dozens of them   ->   1, 2, 1, PASS, PASS
```

`mine_diamond` passes at 30.0 fps inside a full craft sweep (**11/12**) and again at 29.5 on a
recorded run. Baselines: mob **2/4**, the two failures being `mob_trio` and `mob_skeleton`, red since
they were written and gating on damage taken.

### Four candidates came first, and three of them were real bugs

All three shipped in 0.80.0 and none was the cause — worth stating, because each looked like it:

- a `removed=DISCARDED` entity keeps its `getStack()`, so the failure path chased a ghost;
- `_currentDrop` was never released after blacklisting, so the task re-blacklisted its own cached
  target — `Try 1920 / 3` on one live entity;
- `TimeoutWanderTask`'s radius escalated 5, 10, 15, 20, 25 with nothing resetting it.

The fourth was **reverted**: `GetToEntityTask` decides "close enough" with `isInRange(entity, 1)`,
a centre-to-centre test, and an item one block below the player's feet is exactly 1.0 away — so the
test is unsatisfiable even standing on top of the drop. That arithmetic is right, and widening it
changed nothing, because that branch finishes nothing: it resets the progress checker and stops
pathing. A bigger radius only makes the bot stop further out.

### mine_stone is a coin, and every sweep hid it

Measured on both builds, three runs each at a healthy frame rate: `PASS, FAIL, PASS` before the mover
and `PASS, FAIL, FAIL` with it. It fails at least once in **both** arms, so the mover is neither
convicted nor cleared by n=3. What is established is that the course is flaky and every craft sweep
before now recorded it as a clean PASS — because a sweep runs each course once. Take n≥6 before
reading a `mine_stone` verdict.
