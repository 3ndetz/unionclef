# 0.87.0 — the bot finally gets its critical hits

## The bot was claiming crits it never received

Vanilla refuses a critical hit to a **sprinting** attacker, and wants `fallDistance > 0` rather
than merely a downward velocity. Our crit check asked for neither, so every falling swing was
counted as a crit and almost none was granted — a bot closing distance is always sprinting.

It now drops sprint for the one tick the swing goes out on (what human PvP calls a sprint
reset), so the server actually grants the 50%.

Twelve interleaved runs of `allround`, six per arm, read from the victim's own client:

| | crit-sized hits | kills per run |
|---|---|---|
| before | `[2, 3, 3, 0, 0, 1]` | `[12, 13, 13, 13, 12, 12]` |
| after | `[10, 5, 8, 10, 9, 5]` | `[13, 13, 14, 14, 14, 13]` |

Kills +1.0 a run (t=3.16). Total blows are unchanged (38.0 against 37.3) — these are the same
swings upgraded from 6 damage to 9, not extra ones.

**HOW TO TEST.** Duel anything with a sword and watch the damage numbers: falling swings should
now land 9 instead of 6 on an unarmoured target. On the bench:

```
python deploy/runner/run_suite.py pvp --only allround --no-early-stop
```

and read `hit sizes chip/partial/flat/crit` in the verdict — the last bucket is crit-sized hits
and should sit near 8-10 rather than 0-1. To see it against the old behaviour:

```
python deploy/runner/run_suite.py pvp --only allround --no-early-stop --repeat 2 \
    --pin-alt critReleasesSprint=false
```

Turn it off with `@tungsten critReleasesSprint false` if you would rather keep the sprint
knockback on that tick.

## Damage is now measurable at all, and against any target

`dealt` — damage the bot's swings actually removed — printed **0.0 through a fight with seventy
swings and twelve kills in it**. It was not counting: the ledger lived inside a loop that skips
anything which is not a ranged mob, so damage to a zombie was invisible and a player was never
even enumerated. It ticks from the client tick now and books every living target, players
included.

It also reports **what a hit looked like**, bucketed by the vanilla quantities — chip / partial /
a flat 6hp blow / crit-sized — from both the attacking and the receiving side. That is what
made the crit bug visible.

**HOW TO TEST.** In game, `@stats` (or the py4j `placeStats`) now carries:

```
dealt=<ours>/<all>/<ledger ticks>   hitSize=<chip>/<partial>/<flat>/<crit>   takeSize=...
```

Hit something and watch `dealt` move. The third number is the tick count and exists so that a
zero can never again be read as "found nothing" — if it is 0, the ledger did not run.

## Also in this release

- **`syncSlotToServer`** (default **off**): sends the hotbar-slot packet at the switch instead of
  leaving it to the next tick, so a swing cannot be resolved with the item just put away. The race
  is real; removing it measured neutral over six interleaved runs, so it ships off. Try it with
  `@tungsten syncSlotToServer true` if you fight while switching weapons a lot.
- Several counters that outlived their run are now zeroed with the rest. If you were reading
  `slotSync`, `dealt` or `swingHits` across runs, earlier numbers were cumulative.

## Known bugs

- `allround` still loses on the exchange (13 kills against 16 deaths). The bot lands 36-37 flat
  blows to its opponent's 48-50 on a comparable number of swings; weapon, charge, crit count, the
  bow economy and reach control are all measured equal between the two fighters, so what remains
  is blows arriving.
- ~11 hits a run land for exactly 1.0 hp instead of 6. They are real (the receiving client books
  them) and four causes are refuted: the bow in hand, the vanilla sweep, arrows, and a stale
  hotbar slot. Unexplained.
- `mob_trio` and `mob_skeleton` fail; both predate this release (`mob_skeleton` since 2026-08-13,
  on "at most one arrow landed").
- The playthrough still tops out around stone tools.
