# The client stays up

A 30-minute run on 0.95.63 lost its client at minute seven. The crash report:
`NullPointerException: Cannot invoke "List.add" because "HashMap.get(...)" is null` in
`InventorySubTracker.registerItem`, reached from the mob-defence check for a shield. The
inventory tracker rebuilds plain hash maps -- clear, then refill -- and two threads ran that
rebuild at once, so one cleared a map between the other's `put` and `get`. The tracker's update
and every read of its maps are now synchronized on the tracker. It is a rare race (this one came
after four days of client uptime and seven million ticks); the fix rests on that mechanism, not
on a run that happened not to crash.

The test bench also stops calling such a run green: `gamer_smoke` read PASS after 25 minutes with
the client gone, on the rung reached before the crash. Three or more consecutive offline polls now
fail the run with "client left the game".

Measured on the release candidate: `nav_flat`, `nav_staircase`, `nav_water`, `nav_water_pillar`,
`nav_bridge`, `craft_at_distant_table` and `portal_lava_lake` PASS at 29-30 FPS; a 30-minute
native run from `full59-before-portal` PASS with no deaths, no crash, median 29 FPS.

Also on the bench: a `lava_far_lake` course (a lava bucket past 45 capped sources to an open lake);
it passes on this build in about 11 s.

**HOW TO TEST:**

```powershell
python deploy/runner/gamer_smoke.py 30 --from full59-before-portal --raw-resume --record
python deploy/runner/run_suite.py craft --only lava_far_lake,portal_lava_lake --record
```

**Known:** in that 30-minute run the bot later stood 7+ minutes underground "searching for liquid"
for its portal with a lava lake 30 blocks away; tracked, cause not yet found. No speed or FPS gain
is claimed, and the whole playthrough is still open.
