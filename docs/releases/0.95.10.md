# 0.95.10 -- the planner no longer crashes on a transient null world read (G107)

The block-space search runs on its own thread (`FastNavigator-plan`) against the LIVE
`ClientWorld` while the render thread swaps chunk sections in and out. For one read,
`getBlockState` can hand back `null` -- and the planner's block-classification predicates
dereferenced it, throwing `Cannot invoke BlockState.isIn(...) because "$$1" is null` and
failing the ENTIRE plan.

Seen once at the exact moment it mattered: a full `@gamer` playthrough (from the post-iron
checkpoint, day locked) deep-mined to y=2, walked into a cave mob nest (zombie + creeper +
skeletons), switched to the flee task -- and that flee plan hit the NPE, computed no escape
route, and the bot was meleed to death and lost its base. The crash did not cause the mob
encounter, but it removed the one plan that might have gotten the bot out.

## The fix

The planner's block predicates now treat a `null` (unloaded / mid-swap) read as air-like --
which is exactly what vanilla's `EmptyChunk` returns anyway -- instead of crashing:

- `Agent.isClimbing`, `Agent.isFenceLike`, `Agent.getLandingPos` (`isClimbing` is called on
  nearly every node expansion, so it meets the race most often)
- `BlockStateChecker.isConnected`, `isFenceLikeBlock`, `isFenceOrWall`

And `FastNavigator`'s two plan-failure catches now log the top stack frames, not just
`getMessage()`. The message alone named no class or line, which is why locating this site
took a whole diagnosis pass; the next off-thread null read (a `getBlock`/`isAir` variant the
`isIn` guards do not cover) is now pinpointed on first occurrence.

This is a correctness fix for EVERY plan, not only the flee -- any plan can meet the race.
It does NOT by itself stop the bot dying to a cave mob nest during deep mining; that is a
combat/survival matter, tracked separately.

## HOW TO TEST

Verified in the built jar (the source change reaching the shipped bytecode is the thing that
has bitten this project before): `javap -p -c` on `Agent` inside the nested tungsten jar shows
`isClimbing` doing `ifnonnull` / `iconst_0 / ireturn` before the `isIn` (`method_26164`) call.

At runtime the NPE is an intermittent chunk-load race and does not reproduce on demand; a
normal `@gamer` or nav run should simply show no `FastNavigator plan failed` line and no
pathfinding regression.

## Known, not fixed

- Death by cave mob nest during deep mining (day or night) still loses the base; that is
  combat/survival, not pathfinding.
- The post-respawn recovery can wedge trying to reach a canopy log with an empty inventory.
