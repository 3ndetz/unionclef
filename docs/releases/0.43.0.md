# 0.43.0

A production CPU fix: the client no longer runs a full physics simulation every tick just
to feed a debug log that's off by default.

## Per-tick physics sim gated on `verboseDebugLogging`

`MixinClientPlayerEntity` ran `Agent.INSTANCE.tick(world)` — a complete movement
simulation — on **every** client tick, plus a non-executor `compare()` that only prints
the verbose drift log (no side effect). Both existed purely for that debug log. Measured
client CPU on the test stand dropped from **~400% to ~240%** with them gated off.

This is safe because the executor's own drift correction uses the **precomputed path-node
agents** (`Node.agent`), not `Agent.INSTANCE` — and `Agent.INSTANCE` is read nowhere else.
Turning `verboseDebugLogging` on restores the full per-tick sim and the drift log exactly
as before. Navigation is unaffected (verified: the goal-snap course still routes and
arrives; no consistent change on the climbing courses, which are flaky either way — see
below).

## Stand diagnosis, corrected

Earlier notes blamed the stand's "flapping" on unthrottled CPU. That was wrong: the test
container has no CPU limit on a 16-core host and sits at ~2.4 cores — never starved. The
real causes were (1) `slime_test` leaving `verboseDebugLogging` on (fixed in 0.42.0) and
(2) a broken settle-probe calling py4j methods that don't exist. The sim gate above is a
genuine efficiency win regardless.

## Known / tracked

- **Terrain climbing is flaky** (`terrain_test` courses A/B/C): the walker sprint-jumps
  every step-up, which overshoots 1-block staircases, and the grid BFS sometimes returns a
  degenerate stub. A/C fail, B passes intermittently. This is the next core task —
  separating a *walk*-jump (step-up) from a *sprint*-jump (gap), and improving path
  quality — validated to pass consistently before release.
- Core PILLAR place-move (place *up*) and proactive `@goto` bridging remain queued.
