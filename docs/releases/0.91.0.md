# 0.91.0 — the bot stopped fighting itself, and baritone stopped driving

The user watched a recording and found three things in one sitting that a whole session of reading
counters had missed. All three are here.

## Baritone was still driving

`CustomBaritoneGoalTask` handed the goal to the legacy engine whenever the tungsten drive declined
a tick. The counter said so all along — `pdLegacy=9` on a twenty-minute playthrough — and the note
beside it concluded baritone was "nearly dead" from **arena** courses, where it is zero. Nobody
checked the playthrough.

The goal now goes to `TungstenHelper.tryPathTo`, the same call the stuck-recovery path already
makes. If tungsten will not take it, the tick waits.

```
pdLegacy=16   pdLegacyTung=0/16
```

Sixteen hand-offs intercepted, tungsten declining all sixteen, so the cost is sixteen ticks of
waiting in twenty minutes.

## The shuffling had a name, and it was not the one anybody guessed

`TimeoutWanderTask` releases the movement keys whenever the pathfinder is *searching* — guarded by
a check for the close walk to a dropped item, and by nothing else. `BlockPathWalker` drives almost
everything else the bot does and was never asked about.

Widening the key-thief instrument named it on the first run:

```
TimeoutWanderTask:238 x1290   DestroyBlockTask:594 x24   DestroyBlockTask:686 x8
```

Twelve hundred and ninety steals in ten minutes. After the fix that entry is **gone**, and
`DestroyBlockTask:407` — the next line with the same shape — is fixed with it.

The run that measured this reached **stone tools at 66.3 s**, the fastest of the series.

## The camera fought too

The placer has been able to claim the aim for a long time (`placingNow`) and the walker honours it.
The miner never could, so the crosshair swung toward a waypoint while a block broke somewhere else.
That claim now exists, as a timestamp rather than a latch so an interrupted mine cannot freeze the
walk. It is **off by default**: measured at three ticks in ten minutes, it is not the dominant pair
and does not earn a behaviour change yet.

## The instruments were lying, and that is fixed too

- **The bench never reset its counters** on the playthrough. `resetstats` called a method that
  rewrites three dictionary entries and zeroes nothing; the real one was only ever called by the
  arena runner.
- **Runs started somewhere else than the log said.** Spawn points sit at y=150 — air — so the bot
  fell ninety blocks, often died, respawned at world spawn, and the tree count was taken *there*.
  Placement now goes through `spreadplayers` and the arrival is verified.
- **Deaths were never counted.** The mark was an index into a sliding `--tail` window, so on a busy
  server it pointed past the end and printed zero — exactly when the bot was dying. One run
  reported no deaths with six `slain by Zombie` in the server log.

With those fixed, five of six runs score rungs where three did, and a paired A/B yields five usable
pairs out of five instead of one.

## How to compare

```
;settings neverHandOffToLegacy      # on; false restores the legacy hand-off
;settings wanderKeepsWalkerKeys     # on; false restores the key theft
;settings walkerYieldsToMiner       # off; the camera claim, unproven
```

`forwardStealers()` over py4j lists who takes MOVE_FORWARD, commonest first. It is the fastest way
to see this class of bug, and it only ever watched one narrow case before this release.
