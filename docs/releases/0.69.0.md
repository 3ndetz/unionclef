## One unreachable log used to cost you every block in the world

The oldest item on the list — "felling a single log takes minutes in a forest" — turns out not to be
about felling at all.

The chain, end to end, with a counter behind every link:

1. The block ranking sends the bot at a log three blocks away and **seven up**
2. It walks under it and cannot break it — it is out of reach
3. `WorldSurvivalChain` reads "the block did not turn to air" as **a private area**
4. It bans all breaking inside a cube of **radius 50**
5. That is the entire world of the test arena, so nothing is minable at all
6. The search honestly returns no candidates, the bot wanders, and never recovers

```
before:  cb=0/18456/0/0     every candidate refused by the ban     logs=0  firstLogAt=never
after:   cb=0/0/0/0         no refusals at all                     logs=2  firstLogAt=8.2-13.3s
```

A failed break now counts as evidence of a claim **only when the bot actually reached the block**,
judged by the same `blockReachDistance` the reach test uses. On a real protected server the bot
reaches, strikes, and the block survives — the ban fires exactly as designed. What no longer counts
is failing to touch something seven metres overhead.

## The ported heuristic had its Y sign inverted

`GoalYLevel.calculate(goalY, currentY)` treats `currentY > goalY` as descending and `currentY <
goalY` as ascending, and `GoalBlock` passes `current - goal`. The port computed `target - start` —
the other way round — so **every climb was priced as a fall** and every fall as a climb. That is the
ranking the block scanner uses to choose what to walk to.

Verified line by line against the source it was ported from. It also means the climb repricing added
earlier was never reached by an actual ascent.

## The bench could not tell a starved run from a broken one

Two halves of the same defect, both fixed:

- Craft courses never sampled the client's frame rate, so every craft verdict carried
  `avg_fps=None` — and a guard that marks a run INVALID below the healthy line cannot fire on a
  value it never receives.
- The guard *also* whitelists which failed gates a low frame rate may excuse, and every keyword in
  that list named a **nav** criterion. Craft gates read "the bot holds an iron pickaxe"; they
  matched nothing.

Measured while this was being fixed: `craft_iron_pickaxe` FAIL at **9.88 fps** with the smelt half
already finished, on a machine another project was holding at ~470%. It passes 2/2 on a quiet host.
That is precisely the false red the guard exists to prevent, and it had slipped through the repair
aimed at it.

## How to test it yourself

```
@get oak_log 4
```

with a tree nearby and a second, unreachable log overhead. Before this release, one log the bot
could not reach was enough to stop it gathering anything at all.

## Known, and deliberately not fixed here

- The break-avoidance radius of 50 is still disproportionate: one stubborn block silences a
  100×100×100 region. The cause is fixed; the blast radius is not, and it wants its own measurement.
- `craft_at_distant_table` remains flaky with a distinct signature — the bot walks away from its
  target and freezes. Not the same fault; recorded separately.
- Four earlier attempts at this bug were reverted for measuring no change. They are worth knowing
  about: each repaired a link *after* the candidate list had already been emptied by the ban.
