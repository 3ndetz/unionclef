Produced by an 8-reader parallel code audit (melee, ranged, chase, bridge,

## The five root causes behind the live symptoms

1. **RW-1 "stands still near the target" — two clocks fight over the same
   keys.** Combat legs are written twice: `CombatController.combatMove` at
   game-tick HEAD (the write vanilla actually samples) and the
   `SafetySystem.renderUpdate` stage machine at render frequency (~60 FPS,
   sampled never). Whenever a safety stage is active (`NARROW_BATTLE` on
   bridges, `DANGER_BATTLE`/`DANGER_IMMINENT` near edges) combatMove does
   `releaseLegs()` and returns — the render-frame stage keys are wiped one
   line earlier, so the sampled input is all-released: the bot literally
   stands, worst exactly on bedwars/edge terrain
   (CombatController.java:112-115 vs SafetySystem.java:194-285).
2. **RW-1 "stares, doesn't click" — trigger and aimer disagree on the
   point.** The aimer deliberately targets the best VISIBLE hitbox sample
   (head/feet/side) under partial cover; TriggerBot gates the attack on a
   raycast + angle to the hitbox CENTER (TriggerBot.java:67-93). With partial
   cover: aim converges, gate never opens, 100 hitless ticks later punk flips
   back to APPROACH — the observed stare loop.
3. **RW-9 "never catches live, stand PASS" — DIRECT steer self-destructs.**
   (a) the walker's per-tick `groundSafe` bail uses
   `CombatPathfinder.isWalkable(feet)`, false MID-AIR, so every bunny-hop
   bails DIRECT at the jump apex and arms the 2s steer cooldown
   (BlockPathWalker.java:229-241); (b) `setTargetFast` — the fast nav turn
   the walker's own comments rely on to keep the 45° face-before-move gate
   open — has ZERO call sites (dead code), so every bearing change stalls
   sprint behind the slow humanized turn (BlockPathWalker.java:253, 324);
   (c) the steer engage gate raycasts to the target's ground-snapped FEET
   point, which clips terrain lips (fix already known and applied only to
   combat entry, PunkPlayerTask), so DIRECT rarely engages off flat ground
   (FollowEntityTask.java:217-219). Stand tests could not catch any of this:
   every "moving target" was rcon-teleported (zero velocity, 2s stationary
   dwell) on a flat floored arena with permanent LOS.
4. **RW-2/RW-3 "cheaty building" — two placement stacks, the honest one is
   default-off.** The core place-as-a-move chain (PathExecutor.tickPlacing)
   is WindMouse-aim-gated, one block per timing window — and OFF
   (planPlaceMoves=false). Everything visible in the demos uses the cheaty
   stack: godbridge `interactBlock`s the SAME tick it sets the aim target
   (camera is cosmetic) with NO use-cooldown (up to 20 places/s,
   BridgeTask.java:179-185); WorldEdit/fill/build ops funnel into
   `placeBlockAtRaw` = one-shot full-delta camera snap + instant place,
   batched up to 96 cells inside ONE client-thread call — "all 6 glass at
   once" confirmed (Py4jEntryPoint.java:2702-2738, 1861-1867).
5. **#67 "Ran out of nodes" — smartMoves and the capable move-gen are
   mutually exclusive.** `BlockNode.getChildren` returns early under
   smartMoves, never reaching the ONLY branch with break-through,
   place/bridge, water, ladder, slime move-gen (BlockNode.java:292-301); and
   the block-space "A*" never accumulates g-cost (constructor discards move
   cost; relaxation uses `child.cost+1`) — it is a greedy search, all
   SmartMoves costs are dead (BlockNode.java:168, BlockSpacePathFinder.java:275).

## Verified findings by subsystem (critical/high, all CONFIRMED by 2 skeptics)

### Melee (tungsten punk)
- CombatController.java:112 — stage movement neutralized by releaseLegs (root 1). CRITICAL.
- CombatController.java:138-142 — 2.0–3.4 band disables fwd/back/sprint; walk-strafe void-gated per side → hop-in-place on narrow ground.
- TriggerBot.java:74 — LOS gate to center vs aim at visible point (root 2).
- CombatController.java:120-131 — no-LOS + BFS path<2 ⇒ legs released AND no aim target set; camera stale-releases after 600ms = full freeze.
- VoidGuard.java:54-63 — cancels ALL keys + forces sneak when the resultant heading points at a drop; kills rim-parallel strafing (should clamp only the offending component).
- Notable rest: ESCAPE stage unreachable; combatExecutorEnabled never read (30-tick sim burns CPU for viz); zero weapon handling in punk pipeline (no axe/shield/mace; altoclef bestWeapon lives in the legacy path punk doesn't use); braking/repositioning aims camera at horizon (zero attacks in danger stages); wall-clock+Math.random cadences (non-deterministic).

### Ranged
- TrajectorySolver.java:43 — tungsten BowShooter leads off `getVelocity()` ≈ 0 for remote players (the repo documents this itself); only the altoclef path got the position-delta fix. The py4j `shootArrowAt` primitive has NO lead on real players.
- RunAwayTask.java:69 — no shoot-while-fleeing anywhere; every shot is taken standing still; flee executor owns the camera (no WindMouse arbiter) → bow-flee is architecturally impossible today.
- ShootArrowSimpleProjectileTask.java:321 — altoclef release is a pure charge timer, no aim-convergence gate (BowShooter requires 3.5°).
- ShootArrowSimpleProjectileTask.java:263 — rapid-fire releases partial charge while the solver always assumes full-charge speed 3.0 → systematic low shots inside ~20 blocks.
- Rest: KillPlayerTask ranged = 1 arrow/4-10s, branch annotated "TODO NOW UNTESTED"; artillery still legacy g=0.006 closed-form; no trident/snowball/egg primitives; @punk is melee-only.

### Chase / follow / flee
- BlockPathWalker.java:229 — groundSafe false mid-air: bunny-hop self-bails DIRECT every hop + 2s cooldown (root 3a). CRITICAL.
- BlockPathWalker.java:253/324 — setTargetFast dead code (root 3b).
- FollowEntityTask.java:217-219 — feet-point LOS engage gate (root 3c).
- PathFinder.java:120 — physics fallback loses 0.5-3.5s per engagement (500ms startup sleep, frozen-snapshot goal, 0.8-block drift stop, momentum dropped at handoffs).
- follow_altoclef_test.py:159 — the "validating" stand test tp-hops the victim (quasi-static, flat, permanent LOS) — cannot falsify live behavior.
- Rest: BFS walker gated to dist>6 → close-range no-LOS dead zone; RunAwayTask 100% physics-driven with a no-op re-plan race; gap-jumps unreachable outside the executor (tickBFS jump gate scans the gap as unsafe landing); FollowEntityTask leaks searchTimeoutMs into the GLOBAL config (PathFinder.java reads it for every search; only GotoCommand restores).

### Bridge / build
- BridgeTask.java:179-185 — godbridge zero aim gate + zero use-cooldown (root 4). Fix point for RW-3.
- Py4jEntryPoint.java:2702-2738 — fillCells: up to 96 placements in ONE tick (RW-2 confirmed); same pattern replaceStatus/buildBlocks/buildDefenseAround.
- Py4jEntryPoint.java:1861-1867 — placeBlockAtRaw full-delta one-shot camera snap + instant place (flaggable).
- PathFinder.java:257-263 — core_bridge 2/6 flakiness root CONFIRMED in code comments: block search returns a fall-partial with no place plan → physics leg sims across the un-bridged gap and falls; correct fix = physics search completes at the truncated endpoint when places/breaks are pending.
- Rest: bridgeTo is one cardinal leg, computed once, target-Y ignored (cannot chase a moving island target); search-level bridge move same-Y/cardinal/strictly-goal-closer; shredder jump-bridge machine snap-rotates + reflection-resets itemUseCooldown (flaggable set); PathExecutor.tickPlacing/tickBreaking is the aim-gated humanized model everything should converge on.

### Pathfinder core
- BlockNode.java:292 — smartMoves bypasses break/place/water/ladder/slime move-gen (root 5). CRITICAL.
- BlockNode.java:168 — g-cost never accumulated; greedy search; SmartMoves costs dead. CRITICAL.
- PathFinder.java:108 — no goal-retarget: find() silently no-ops while active; chase re-plan = stop+wait+restart with 2s/3-block hysteresis.
- FollowEntityTask.java:186 — hold-position early-return inside closeEnough; enableLeap default false; <6-block search budget 120ms behind 500ms overheads → close-range dead zone.
- BlockSpacePathFinder.java:143-148 — budget applies only once `failing` clears (5 blocks progress) → unbounded CPU spins on open terrain.
- BlockPathWalker.java:313/338 — waypoint tolerance 1.5 + 45° sprint gate vs 1-wide bridges (corner-cut falls); NO void/edge cost in any search.
- Rest: TungstenHelper reflection bridge dead (silent no-op fallback); minPathSizeForTimeout dead knob; static search state races.

### Test infra (why the suite was rebuilt)

### Control surface (levers) — gaps that block assertions
- No kite/bow-flee lever (CRITICAL for the bow-flee scenario).
- No in-band fight telemetry: punkStatus/runAwayStatus = {active,target} only; no followStatus, no re-plan/bail counters, no swing/hit events (CRITICAL for "never pauses / never re-routes" assertions; suite v1 falls back to 1s rcon sampling).
- No bowStatus (BowShooter.isActive/getShotsFired unexposed).
- No determinism levers (unseeded WindMouse Random, wall-clock cadences).
- combatBunnyHop* are `long` fields — SettingsCommand only generates setters for bool/double/float/int ⇒ NOT settable via ;settings (the v0.49 "live-tunable" claim is half-true).
